# Legacy Metal fixes: what each one does

The fixes in this folder, grouped by the file they ship in, with the bug each one works around, how it was found and
the test that shows it (`Tests/`, run by `verify.sh` without and with the fix):

- `sNN`: `MetalOldCompat.dylib` (Metal framework level) and `AMDBronzeCompat.dylib` (12.5 AMD driver)
- `aNN`: `AMDTextureAtomics.dylib` (12.5 AMD shader compiler)
- `cNN`: the libAMDIL902 patches
- `iNN`: `IntelTextureAtomics.dylib` (3802 Intel shader compiler)
- `rNN`: guards that keep a fix from regressing

Most fixes can be switched off for a test with an environment variable (`MTLSHIM_*`, `AMD_*_FIX`, `INTEL_*_FIX`), named
in the source next to each one.

## 1. `MetalOldCompat.dylib`

Loaded by the Metal.framework wrapper in `13.2.1-24` and `13.2.1-25` (Tahoe), so in every Metal app. Source: `MetalOldCompat/MetalOldCompat.m`.
- Adds the macOS 13.3-15 Metal methods MetalOld lacks. Chrome calls `setMathMode:` on every shader compile and aborts without it. (s01, s08)
- Makes reflection data from the newer compiler readable (s02), accepts `MTLTextureUsageShaderAtomic` (s03), and converts vertex-descriptor layout records between the two formats (s07).
- Accepts MSL 3.2 requests, which Firefox's WebGPU and MoltenVK make on Sequoia. (s09)
- Fixes a device over-release crash in MetalOld's device list that killed Chrome's GPU process. (s10)
- Lets ANGLE (Chrome, Safari, Electron) past its Mac-model check and gives it the GPU that can run WebGL here, the AMD card (family 2). On Macs whose only GPU is the Intel one (family 1), ANGLE refuses it, so there it's presented to ANGLE as family 2. ANGLE's own fallbacks are switched on, through `ANGLE_FEATURE_OVERRIDES_DISABLED`, for the three family-2 features the Intel driver lacks (swizzled texture views, stencil MSAA resolves, pipelines without attachments) and for depth comparisons with gradients, which the Intel compiler can't build. Dawn (Chrome's WebGPU) hears the same family-2 answer, except for two questions that get the real one: whether to offer subgroups (the Intel compiler can't build SIMD-group reductions, and the compiler service aborts) and whether to offer texture-component-swizzle (no swizzled views). The shim recognises both by the order and closeness of Dawn's family checks; ANGLE's checks still get family 2. (s31; `chrome://gpu` shows the rest)
- Works around Intel driver bugs: MSAA resolves (s15a), narrow clears (s15b), 2D-array views (s16), 8-byte buffer fills (s20), depth-only pipelines (s21), HiZ on depth textures with several levels or slices (s22), 3D mip planes (s23), R8/RG8 clears at mip 1+ (s24), and depth and stencil written by blits, which later render passes didn't see (s32). ANGLE copies stencil that way on Intel GPUs, so `glBlitFramebuffer` lost it. More Intel driver workarounds follow below.
- Safari:
  - compiles ANGLE's internal shaders from source, because Safari's prebuilt metallib targets macOS 15.4;
  - restores the argument encoders that the wrapper stubs out for processes with "Safari" in the path (s14).
- Fixes the pipeline cache key. MetalOld cached compute pipelines per function and ignored the descriptor. Blender asked for a 1024-thread pipeline, got the cached 768-thread one, dispatched 1024 threads and hung the GPU. That was the EEVEE crash. (s18)
- Compiles shader libraries built for macOS 15.4 and later (AIR 2.7, newer Xcode). Sequoia's compiler reads them, but MetalOld asks it for the macOS 14.2 target, so it rejected them: iMovie 10.4.4's viewer stayed black and nothing played. In the compiler service, such modules are now retargeted to AIR 2.6, the same change MetallibSupportPkg makes to Sequoia's system metallibs. (s13)
- A divide by zero in WebKit's WebGPU, which only traps on Intel Macs. `beginRenderPass` rounds up to a multiple of a format alignment that is 0 for a canvas texture destroyed by a resize. On Apple silicon `udiv` by zero gives 0 and validation reports the error; on x86 the SIGFPE kills Safari's GPU process and every page then gets a null adapter. A handler in WebKit's processes gives the `udiv` result for divides in the WebGPU framework. It resumes the code itself, because `sigreturn` fails in that process. (s28, needs Safari and an installed system)
- Photos' portrait editing crashed on every 3802 GPU (OCLP issue #1008), in `CoreImageOld.dylib`, the 14.0 beta 3 Core Image these payloads install. It loads its portrait kernels from a static `NSData` that it never retains (the once-block stores `[NSData dataWithContentsOfURL:]` of `CIPortraitBlur*.metallib` as is), so after an autorelease pool drains, `CIDepthBlurEffect` passes a dangling pointer to `-[CIKernelLibrary initWithData:error:]`. Where `CoreImageOld.dylib` exists, those files come from a cache that keeps them alive. The filters render now, but the blur isn't applied (Limitations). (s53)
- More 12.x Intel driver workarounds:
  - The emulated argument-buffer encoder dereferences a nil buffer, which Metal allows in an unused slot; Cycles in Blender 3.6 crashed at its first GPU sample. The slot is cleared instead. (s33)
  - WebKit's sample mask of 0 draws every sample on this driver too (as on the AMD one, item 5); in WebKit's processes it becomes a mask that covers nothing. (s30)
  - Integer cube textures with 1x1 or 2x2 faces sample as 0 in vertex and fragment functions: the sampler asks for seamless cube addressing, which it can't do for integer formats on faces that small. Nearest samplers get programmed addressing, which reads the same texels. WebGL's integer cube map pages. (s34)
    A nearest gather's 2x2 footprint does span face edges, though, so cube gathers through such a sampler came back clamped (WebGPU CTS `textureGather` `sampled_3d_coords`, nearest: 330 cases). The Intel adapter gives cube gathers in vertex and fragment functions a linear constexpr sampler, which stays seamless (a gather doesn't filter, and seamless addressing ignores the address modes). `sampled_3d_coords` now fails only `rg32float`. (i20) Samplers with a compare function get the clamped addressing too: ANGLE passes GL's default compare function (`LEQUAL`) to every sampler, comparison on or off, so leaving them seamless (tried for WebGPU's compare gathers) broke every WebGL integer cube again (s52). A cube `gather_compare` at a face edge through a nearest compare sampler therefore reads one face (WebGPU CTS `textureGatherCompare`, 60 cases), the smaller loss.
  - LOD clamps passed to the 12.x Intel driver's encoders (`setFragmentSamplerState:lodMinClamp:lodMaxClamp:atIndex:` and the like, every stage) wrap modulo 16: 1000 reads as 8, −3 as 13. Clamps set in sampler descriptors are saturated correctly. ANGLE binds every WebGL texture's sampler with GL's default range (0, 1000), so in Chrome and Safari WebGL never sampled a mip level above 8, for any texture over 256 texels. The clamps are clamped to the field's range first. `conformance2/glsl3/texture-bias.html` now passes. (s35)
  - Texture views with a swizzle come back nil from the 12.x Intel driver; family 1 has no swizzle. Item 11 tells Chromium a lone Intel iGPU is family 2, and Dawn (Chrome's WebGPU) then makes every depth/stencil view it needs with an R001 swizzle, so the device was lost on every stencil8 render pass and every shadow map. Where the swizzle changes nothing a shader can see (the identity, a format's own channels, R001 on depth/stencil), the view is made without it. Arbitrary swizzles remain unsupported, and Dawn is no longer told to offer WebGPU's texture-component-swizzle (see item 11). (s36)
  - Stencil textures with several mip levels or slices: on the 12.x Intel driver, render passes on them and blits into them disagree. A pass at another level or slice doesn't load what's there, and a pass that loads and stores level 0 makes shaders read every subresource as that pass saw it, which also undid item 27. Render passes on such textures go through a temporary single-level texture, copied in and out by blits. This fixes s17 on Intel and the WebGPU CTS depth/stencil copy tests. (s37, s17)
  - Coverage a fragment function computes (a `[[sample_mask]]` output, or alpha with alpha-to-coverage) travels with the color write on the 12.x Intel driver. In a pipeline with no depth or stencil attachment and every color writeMask none, it's dropped: every sample counts as drawn, so occlusion queries count them all. Dawn implements `GPUMultisampleState.mask` with a sample-mask output. Such multisampled or alpha-to-coverage pipelines now write their first blendable color attachment through a blend that leaves it unchanged (source × 0 + destination × 1). WebGPU CTS `occlusion_query,sample_mask` and `alpha_to_coverage` with writeMask 0 (56 cases). (s38)
  - Metal Performance Shaders' image statistics finish with a `compute_final_*_statistics` kernel that reduces through threadgroup memory and assumes at least 32 threads (it always folds in `tg[tid + 16]`). MPS dispatches it with the pipeline's `threadExecutionWidth`, which on these Intel GPUs is 16, so the first step reads past the threadgroup memory as 0. `MPSImageStatisticsMinAndMax` returned minimums of 0 (and maximums of 0 for negative data), and `MeanAndVariance` returned wrong means and variances. Core Image's `CIAreaMinMax` runs on it. Those MPS pipelines (MPS labels them by function name) are dispatched with 32 threads and matching threadgroup memory on the Intel GPU. A sweep of all 211 built-in Core Image filters, GPU against Core Image's CPU renderer, found no other GPU-specific differences; the MPS matrix kernels (multiply, softmax, top-k, matrix-vector) were already right. (s39)
  - Multisampled Stencil8 textures on the Intel driver: render passes write their stencil right, but shaders read it wrong. Past the largest power of two below the width, most rows read the left half again (a 4x 256x128 texture: 14464 of 32768 texels wrong). ANGLE reads a `GL_STENCIL_INDEX8` multisampled renderbuffer that way to resolve or blit it. Depth32Float_Stencil8's stencil reads right, also as a stencil-only attachment with a pipeline that declares Stencil8, so these textures are created as Depth32Float_Stencil8 (5 bytes a sample instead of 1), and Stencil8 views of them become X32_Stencil8 views. dEQP `fbomultisample` 2, 4 and 8 samples now pass in Chrome. `MTLSHIM_MSAA_STENCIL8=0` turns it off. (s40)
  - Stencil copied between a buffer and mip level 1 or higher on the Intel driver loses texels when the buffer offset or `bytesPerRow` isn't a multiple of 256: some come from their left neighbour (at mip 2 of a 20x16 texture, the 5th texel of each row reads or writes as the 4th), for Stencil8 and the stencil of Depth32Float_Stencil8 alike. Dawn copies a tight buffer's last row on its own with `bytesPerRow` set to its width, so WebGPU copies lost their last texel. Such copies go through a level-0 temporary texture of the same format (texture copies are right at every level). `MTLSHIM_STENCIL_COPY=0` turns it off. (s41)
  - Stencil views (X32_Stencil8) of Depth32Float_Stencil8 read 0 at mip level 2 and above for many widths on the Intel driver: the view describes the stencil plane with the depth plane's horizontal mip alignment (4), but the plane is laid out with 8, so levels 2+ (to the right of level 1) are looked for in the wrong place whenever level 1's width rounds differently. Dawn backs WebGPU's stencil8 with that format. Stencil views get alignment 8. `MTLSHIM_STENCIL_VIEW_ALIGN=0` turns it off. (s43)
  - Size queries (`get_width` / `get_height`) on writable 2D-array views that start at mip level 1 or higher returned level 0's size in fragment functions: there the driver binds the view's render-target surface state, whose min LOD is 0 (its LOD field holds the level, which only writes read). WebGPU CTS `textureDimensions` storage: 40 cases. That state's min LOD is set to the level, which only the sampler reads. `MTLSHIM_TARGET_MIN_LOD=0` turns it off. (s45)
    The same render-target state kept the whole texture's layer count (Depth) for a 2D-array view whose first layer isn't 0, so `get_array_size()` on a writable view of layers 11-16 returned 17 in fragment functions (WebGPU CTS `textureNumLayers` storage, write, partial views: 40 cases). The view's Depth is copied in; writes still land at the view's layers. (s49)
  - The shim's own replacements for methods that return an owned object (texture creation, texture views, the reflection inits, `MTLCompileOptions`' init) handed it back autoreleased instead. Apps with a run loop drain their pools regularly, so there it only kept textures and views alive a little longer; in a process that drains none (dawn.node, command-line tools) every one leaked: WebGPU CTS `image_copy` had 15000 textures alive after 25 s and grew past 13 GB. They now return owned objects. (s42)
  - Depth comparisons (`sample_compare`, `gather_compare`) in compute kernels through a sampler argument always returned 0 on the Intel driver: its compute path builds the sampler's hardware state (`CHAL_INTEL::ChalContext::PatchSamplerObject`) from the kernel's template and the sampler's filters, address modes and LOD clamps, but leaves out the compare function. Constexpr samplers and vertex/fragment functions were right. The function is wrapped (an inline hook, its first 42 bytes checked against this driver build) to copy the compare function in afterwards. WebGPU CTS `textureGatherCompare`: 900 of 900 now (was 540). (s50)
    The same template has LOD PreClamp Enable clear, so the hardware picked the min or mag filter from the unclamped LOD: a level at or below 0 read the base level alone even with a `lodMinClamp` of 0.25, which should blend a quarter of level 1 in. That bit is copied from the sampler object too. WebGPU CTS `textureSampleLevel` `lodClamp` in compute: 90 cases to none. `MTLSHIM_COMPUTE_LOD_PRECLAMP=0` turns it off. (s51)

- Metal's validation layers (item 41): Sequoia's and Tahoe's MetalTools (`MTL_DEBUG_LAYER=1`, Xcode's API validation) and shader validation (`MTL_SHADER_VALIDATION=1`) are built for the OS's own Metal. On MetalOld, API validation crashed on every compute dispatch (it calls `validateDispatchThreadsPerThreadgroupWithRTPTG`, which the Metal wrapper only exports as placeholder data), asserted "Bicubic filtering of 16-bit normalized values is not supported" on an indirect command buffer (MetalOld numbers `MTLValidateFeatureSupport`'s features differently), and rejected a matching render pipeline with values read by the new layout ("colorSampleCount (1065353216)"), aborting the process; shader validation instruments shaders with the OS's compiler, whose AIR the legacy compiler rejects. Both are switched off before a device is made, with a note on stderr, at load and in `MTLCreateSystemDefaultDevice` / `MTLCopyAllDevices` for programs that set them at run time (wgpu's GPU tests aborted). `MTLSHIM_VALIDATION=1` keeps them. (s54)

## 2. `AMDTextureAtomics.dylib`

Weak-loaded by AMDShared (`12.5`, and `12.5-GCN-25` on Tahoe), AMD shader compiles only. Source: `AMDAdapter/`.
- Texture atomics (MSL 3.1), which the 12.5 compiler drops silently. EEVEE's shadows need them. (a01)
- Textures and samplers reached through a pointer stored in memory get a garbage descriptor. WebGL sampler arrays indexed in a loop render black, and one hung the GPU in Chrome. (a05)
- GCN 1.0 (Southern Islands) only; other GPU families are left alone:
  - Missing wait states before scalar buffer loads: wrong uniform values in WebGL 2. (a02)
  - Stale reads right after a write: black blocks behind glass and water in EEVEE. (a03, needs Blender)
  - Threadgroup memory read at the wrong address through a stored pointer: EEVEE depth of field. (a04; r01 guards the fix)
- Compares that must be false for NaN. Metal's fast-math default marks every function `"no-nans-fp-math"="true"`, and the 12.5 compiler's LLVM then compiles `if (x > t)` so that a NaN takes the branch. EEVEE's `safe_normalize()` of 0/0 (the world sun, when the world has no sun) returned NaN instead of its fallback, which zeroed all volume lighting. The adapter sets the attribute to false; the other fast-math options stay. (a06)
- `ldexp` on `half`. libAMDIL902 crashes on `half3` (it widens vec3 intrinsics by name, and has no `air.fast_ldexp.v4f16`) and returns wrong values for the other widths. The adapter computes in `float`, where every `half` is exact. WebGPU CTS `builtin,ldexp:f16`: 12 failures to none. (a07)
- `gather` on integer textures. libAMDIL902 asks `fetch4` for unnormalized coordinates but passes normalized ones, so every call returns the texels at the texture's corner. The adapter switches the IL to normalized coordinates and subtracts half a texel, because GCN forces nearest filtering on integer formats. 2D and 2D array only. WebGPU CTS `textureGather:sampled_2d_coords`: 756 failures to none. (a08)
- `gather` on integer cube and cube array textures. On cubes no shifted direction fixes a08's footprint: near a face edge it takes texels from the neighbouring face, and integer `fetch4` doesn't cross edges. The adapter turns these gathers into four nearest samples at level 0, at the centres of the footprint's texels, found in face space with Metal's face selection (a centre past an edge moves onto the neighbouring face's edge row). WebGPU CTS `textureGather` `sampled_3d_coords` and `sampled_array_3d_coords`: 252 integer cases to none; results match the M3 and the Iris Pro at faces of 8, 64 and 512 texels, edges included. (a17)
- Bitcasts of a vector to narrower lanes (`<2 x i16>` to `<4 x i8>`, from `as_type<uchar4>(ushort2)`, or from the front end itself when only the low bytes of `ushort2` lanes are used): libAMDIL902 leaves the other byte of lane 1 in byte lanes 2 and 3, so the bytes read back wrong once stored. The adapter builds such bitcasts lane by lane. That was all 29 of the AMD failures in the 11,5 session's narrow-vector fuzzing. (a18)
- Float atomics on device memory (MSL 3.0 `atomic_float`: `fetch_add`, `fetch_sub`, `exchange`, `compare_exchange`) crash libAMDIL902, although the GPU reports Mac2. Exchange and compare-exchange run on the integer bits; add and sub use a compare-exchange loop whose retries take the value the failed exchange read (from L2) rather than a possibly stale cached load. 4096 threads on the same addresses give exact sums and unique exchanges, as on the M3. (a19)
- 64-bit integer comparisons that feed a select or a branch make libAMDIL902 stop with "Cannot select"; they're done on the 32-bit halves. (a20)
- Branches on one bit of a 64-bit value (`if ((x >> k) & 1)` on a `ulong`, or the bit-0 split of a `switch` on `uint(x >> k) & 3`): libAMDIL902's DAG combiner turns them into a compare of the 64-bit `and` with 0 whose result is i64, and no pattern takes it ("Cannot select: brcond (i64 setcc ...)"). A bool of high-half bits of a 64-bit product that is sign-extended or selected on meets the same i64 compare in a select. The adapter tests such bits through `extract_bits`, which the combiner doesn't look into. A bool worked out from a 64-bit value in an earlier block meets it too: `bool(a & b)` of 64-bit-derived halves, sign-extended after a loop, came back there as an i64 compare (the 64-bit value arrives with its top half known zero), so such conditions go through `extract_bits` in their users' blocks as well. (a21)
- Signed division or remainder of 32 bits cut from a 64-bit value, `(int)uint(x >> k) / c`, comes out as the unsigned division: libAMDIL902 seems to take the known-zero top bits of the 64-bit value for bit 31 of the cut. The same for any 64-bit value with known-zero top bits, as `(int)uint(x % y) / c`. The adapter builds such dividends from the 32-bit halves, or passes the low half through two 16-bit `extract_bits`. (a22) Also when the cut reaches the division through a loop variable (`uint v = uint(x >> 10); for (i < 3) s += int(v) % 257;`): the AIR keeps the loop, and libAMDIL902 unrolls it afterwards, so the first division saw the cut. (a27) The cut can also pass an unsigned division, remainder or right shift on its way: `(int)(uint(max(x, y) >> 14) / d) / 225` was unsigned for negative quotients (seed 4769); cuts up to two such steps back are built from the halves too. (a22 form 9) A cut of a 64-bit product, `(int)uint(((ulong(a) << 32) * y) >> 24) / 51`, goes through the extracts instead: built from the product's halves, libAMDIL902 took its high half wrong (seed 763, a regression of this fix). (a22 form 10)
- `z + uint(bool(x & min(1u, 145u)))` comes out as `z - bool`: `air.min` / `max` / `clamp` with constant arguments stay calls through libAMDIL902's IR optimizer and fold only in its DAG, where the and with the now-constant 1 is taken for a 0 / -1 boolean. `y % (min(x, 1u) | 1u)` crashed its bit-field-extract combine. The adapter folds such calls to constants, and unsigned `min(x, 1)`, `min(x, 0)`, `max(x, 0)` to `x != 0`, 0 and `x`. (a23) When the constants appear only after unrolling, as `for (i < 3) a += uint(bool(x & min(i, 145u)))`, 32-bit calls whose arguments are constants or loop values become a compare and a select, which the IR optimizer folds after unrolling. (a28) `min(b, y) | 1` with b a bool crashed the same bit-field-extract combine as `min(x, 1u) | 1u` (seed 4629; the front end writes `(min | 1) & 0x7fffffff` as `(min & 0x7ffffffe) | 1`): a min with a 0 / 1 argument, or the constant 1, has its `| odd` folded to the odd constant and its `& even` to 0 (a23 forms 7 and 8); the 0 / 1 argument may also be such a value divided, shifted right or taken modulo something, as `uint(int(bool(..)) / int(d))` (seed 3734, a23 form 9).
- A zero-extended 32-bit value shifted into both halves of a `ulong` (the front end makes `(ulong(min(c, a)) << 32 | rhadd(b, a)) * k >> 19` into `(ulong(min) << 45 | ulong(rhadd) << 13) * ...`) lost the bits that cross into the high half: libAMDIL902 takes the top bits of `rhadd` / `hadd` results for known zeros. The adapter builds `ulong(y) << k` (0 < k < 32) from the halves. (a24)
- A loop exit on the low bits of a square: the front end makes `((x * x) << s) & 3 == 0` into `((x & 1) & (3 >> s)) == 0`, libAMDIL902 takes `x & 1` for a 0 / 1 boolean, drops the `& 1` and tests the whole register, so for x = 2 mod 4 the loop ran on. The bit-test fix (a15) sends that `x & 1` through `extract_bits` too. (a25)
- `bool(~b & uint(bool(a))) | (a & 0xffff)`: the IR's `or (and (zext (a != 0)), ~b), (and a, 0xffff)` sends libAMDIL902's bit-field-insert combine to read operands of an operand that has none ("Compiler encountered an internal error"). The adapter builds that `and` as `select (a != 0), (~b & 1), 0`. (a26)
- A byte or short cut from lane 1 or higher of a vector, as `uchar(max(ushort2 a, b).y)` stored to threadgroup memory, read 0 when the same block also had a `uchar2` comparison: once type legalization has changed the block, libAMDIL902's DAG combiner folds the truncated lane into an extract of the vector bitcast to narrower lanes, which it builds from the wrong bits of the lane (a18's bug, reached from the DAG). The adapter cuts such lanes, and bitcast lanes from wide lane 1 up, through `extract_bits` (same switch as a18, `AMD_BITCAST_LANE_FIX`). (a29)
- `clamp(x, c, c)` with x not constant: libAMDIL902's DAG folds it to c through the known bits of x (`clamp(y | 1u, 1u, 1u)`), so the a23 case came back (`z + uint(bool(x & clamp(y | 1u, 1u, 1u)))` was `z - bool`). The adapter folds a clamp with equal bounds to the bound; lo > hi is undefined in MSL and left alone. (a30)
- An inner loop's exit on bits of a value and'ed with (or shifted by) the outer loop's counter, `for (i < 3) { while (...) { v ^= ...; if ((i & v & 3) == 0) break; } }`: once libAMDIL902 unrolls the outer loop the test is `(v & 1) == 0`, a15's bug, which the bit-test fix only saw with a constant mask; the inner loop never stopped for i = 1. Such ands (`== 0` / `!= 0`, with a loop counter anywhere in their arithmetic, through selects and the phis the front end makes of them) go through `extract_bits` too. In the same vein, a23's `min(x, 1u)` → `x != 0` made 0 / 1 values that a15's bug misread in a loop exit (a kernel the stock compiler gets right); `min(x, 1u)` now stays a call and only `min(x, 1u) | odd` is folded. (a31, a23 form 6)
- The high half of a 64-bit product whose operand has an unsigned average in its low half, `mulhi((ulong(a + b) << 32) | rhadd(a, b), (ulong(popcount(86u)) << 32) | k)`: it came out 2 too low for most inputs when the other factor folds to a constant late (a literal 4 hides it); libAMDIL902 seems to drop carries out of the average, as with a24's top bits of hadd / rhadd. The adapter builds unsigned 32-bit hadd / rhadd that are widened to 64 bits from bitwise arithmetic, which can't overflow. (a32)
- An inner loop that some lanes of a wave leave early (a `break`, or a data-dependent exit) inside an outer loop that libAMDIL902 unrolls fully: the lanes that had left still took the values of the inner loop's later passes, so `for (i < 4) { while (n < 8) { ...; if ((int(i) / d & 3) == 0) break; } }` came out wrong in every lane of a wave with one lane that loops on. The adapter puts `llvm.loop.unroll.disable` on outer loops with a fixed trip count that hold such a loop whose exit depends on the outer loop's counter. Taken more widely (any outer loop around a loop with a break or a loaded bound), it kept loops rolled in half of Apple's MPS kernels, and Geekbench 7's Background Blur, Face Tracking and Super Resolution failed their validation. (a33)
- The high half of a 64 x 64 bit unsigned product, `mulhi(ulong, ulong)`: with one factor's high half a large power of two (2^31, 2^30) and the other's from a right shift (`ulong(x >> 16) << 32 | y`), the high 32 bits came out as if that high half were 0, in every thread (stock files too). libAMDIL902's 64-bit multiply is at fault, so the adapter builds every scalar unsigned 64-bit `mul_hi` from 32-bit `mul` and `mul_hi` of the halves, with the middle terms' carries. a32's average was most likely the same bug. (a34)
- Constant rotates by a multiple of 8: SC folds the IL's bitalign the other way once it knows both operands (`rotate(37u, 24u)` gave 0x2500), so the adapter writes rotates as shifts. Only rotates that can meet that bug are rewritten now: made shifts, `rotate(~0u, 1u << 31)` folded to a constant that turned `uint(x % (ulong(rotate(~0u, ..)) << 32 | 1))` into an i64 compare in libAMDIL902's optimizer, which no select pattern takes (seed 5463; stock files compile it). Rotates of 0 or all ones, and by constants that aren't a nonzero multiple of 8, stay calls. (a14)
- A test of the low bit after an `if` that may change the value, `r = (a & 1) ? 0 : b; if (r < d) a ^= ...; s = (((a & 1) ? d : 1) & 1) ? ... : ...`: the front end tests a phi of the two `a & 1` values. Once the bit-test fix had made the first test an `extract_bits`, the phi was the `and`'s only user and libAMDIL902 dropped its `& 1`, so 72 of 256 threads took the wrong arm (a regression of that fix: stock files compile it right). The fix now sends the phi's `and`s through `extract_bits` too. (a15 kernel bitphi)
- A single-bit test on 16 bits in a loop exit: `s = select(short2(1, 1), short2(..) & short2(-12131, -9348), ..)` has bit 1 known zero, so the front end makes `(uint(s.x) ^ uint(s.y) * 257) & 3 == 0` into `(s.x ^ s.y) & 1` on `i16`, which a15's bug misreads: the exit tested the whole 16 bits, and 72 of 256 threads ran all 8 passes (stock files too). The bit-test fix only took 32-bit `and`s; 8- and 16-bit ones now go through `extract_bits` of the zero-extended value. (a15 kernel bitshort)
- `(min(150u, K) > b) != bool(min(1u, 104u) & (c / 1522195843u))`: the min/max fix (a23) folds `min(1u, 104u)` to 1 where the call was, so the `and` reads `1 & y` with the constant first, which the bit-test fix didn't recognise; libAMDIL902 then dropped the `& 1`, and y = 2 took the wrong branch in 81 of 256 threads. The bit-test fix now finds the mask in either operand. (a15 kernel maskfirst)
- A `switch` on low bits in an unrolled loop: `for (i < 3) { s = short2(short(i), short(v)) & short2(5474, 29237); switch ((uint(s.x) ^ uint(s.y) * 257) & 3) .. }`. Unrolled, only bit 0 of the switch value varies for i = 0 and 1, and the lowering's bit test misread it (a15's bug): 118 of 256 threads took the wrong case (stock files too). Switch values that are `x & (2^w - 1)` (or the zext of an 8- or 16-bit one) now go through `extract_bits(x, 0, w)`. (a15 kernel switchbit)
- A single bit compared with a bool in an unrolled loop: `for (i < 3) if (((c & 1) % (i | 1)) == uint(!((a ^ (t << i)) > b))) r = ...`. The front end compares the remainder with the zero-extended bool, and libAMDIL902 dropped the `& 1` as in a15, and 62 of 256 threads took the wrong branch (stock files too; the same compare without the `%` or without the `!` is right). In `x == b` / `x != b` with b a zero-extended bool, the `y & 1` in x, directly or under an unsigned division, remainder or right shift, now goes through `extract_bits(y, 0, 1)`. (a15 kernel bitbool)
- The narrow (8- and 16-bit) integer operations libAMDIL902 gets wrong are done in 32 bits, but unsigned operations on provably exact values (small constants, arguments, loads, non-wrapping arithmetic and bitwise operations of exact values) stay native, so loop counters keep a trip count the compiler can see. Without that, Apple's MPS kernels (`ushort` loop counters and thread positions) failed Geekbench 7's validation and its Super Resolution took 25 minutes instead of 47 s. Geekbench 7 Metal now validates every workload on the R9 M370X. A narrow vector loaded from a buffer and also used as an integer (`char4(..) != as_type<char4>(in[i])` beside `ushort(in[i])`, which the front end loads once as a char4) is widened lane by lane from its bits: its zero extension became an extending <4 x i32> load that libAMDIL902's combiner left the integer use on, "Cannot select: i32 = bitcast" (seed 675; stock files compile it). (a16, kernel loadedvec)
- A cube array index below 0. GCN clamps the slice, `8 * index + face`, so -1 reads the first face of the first cube whatever the direction. WebKit and Firefox pass WGSL's index on as it is, and WebGPU asks for the nearest layer. The adapter raises the index to 0 first. WebGPU CTS `shader,execution`: 2414 Safari failures and 2053 Firefox failures gone. Safari fails the same cases on an M3 Pro, so this goes further than matching Apple silicon. (a09)
- `threadgroup bool`. LLVM shrinks a threadgroup variable that only ever holds two values to an `i1` global, and libAMDIL902 miscompiles `zext` of its load: `iand load, r`, with `r` holding an unrelated 0, so it always reads as false. The adapter loads the byte and compares it with 0. WebGPU CTS `workgroupUniformLoad:types`, `type="bool"`, in Safari. (a10)
- Multisample texture reads on the `12.5-24` driver (Sequoia without MetalOld), from riptidewave93. A `texture2d_ms` read first loads the texture's FMASK descriptor from a table (API slot 13) that this driver copy never sets for render stages, so a fragment shader loads from GPU address 0 and the GPU resets; compute reads get wrong samples. Safari reset the GPU on every antialiased WebGL canvas. Only on Sequoia (Darwin 24) where OCLP's `impostor.dylib` is installed: Tahoe's `12.5-25` and `12.5-GCN-SKL-25` link it too, but set the FMASK table, and there the identity map reads the wrong samples (a11 and s25 failed, wrong colours in Chrome and VS Code). `AMD_FMASK_FIX=0/1` forces it off or on. (a11)

In fragment functions, the z of a float3 input passed straight to `sample_compare` is compared using the input's x instead; ANGLE passes `sampler2DShadow` coordinates as a vec3 varying exactly that way. Float3 vertex and fragment inputs are read through `fmax(a, a)` first. dEQP `swizzles_vec3`, `conversions_vector_to_scalar` and the `sampler2dshadow` fragment cases now pass in Chrome. (i06, i09)
- Samplers in compute kernels blend between mip levels only in the middle quarter of each step on Haswell. Explicit levels in compute kernels are remapped so the blend comes out linear. (s19 on Intel; Haswell only)
- `threadgroup bool`: the back end can't select `i1` loads and stores in threadgroup memory. Widened to bytes. (a10 on Intel)
- Byte and halfword loads from private memory with 16-byte alignment (the first small field of a struct in a dynamically indexed private array, as in EEVEE's G-buffer writer) have no instruction pattern. Done on their 32-bit word. (c03 on Intel)
- Small private arrays indexed with a variable (ANGLE declares every GLSL array as a `metal::array` inside a struct): in vertex and fragment functions the back end keeps them in an indexable register array that it addresses two ways (byte addresses for stores at constant offsets, element slots for variable indices), so elements written one way and read the other came back 0 or stale (WebGL `unary-minus-operator-in-dynamic-loop`, dEQP `shaderstruct` `array_member_dynamic_index`). Variable-index loads and stores into arrays of up to 16 elements become accesses at every constant index plus selects. (i07) This takes every such array, not only those also written at constant offsets: an array only ever indexed with variables, read and updated in a loop, is wrong too (250 of 256 threads; i34), so narrowing it that way breaks things. And it takes an array whole or not at all: a variable-index store the front end wrote through a bitcast (`p[i] = x` stored as `<2 x i16>` because `x` was also used as a `ushort2`) was left alone while the array's other one was rewritten, and that mix gave wrong contents in every thread (`mslfuzz2` VEC seed 1469; the stock compiler is right). Loads and stores through a same-size bitcast are done in the element's type now. (i44)
- A private array that a pointer select also reaches (`thread uint *q = c ? &p[6] : &p[5]`) stays in private memory, and there the back end forwards a load of an element past a store to that same element: after `p[5] = p[5] + a; p[5] = p[5] * 3u;` the multiplication uses the value the first statement loaded. The stock compiler does this too. The i07 rewrite turns every variable-index store into such loads and stores, so random integer compute kernels with a pointer select came out wrong 43% of the time (differential fuzzing against a CPU reference on both 2015 MacBook Pros). Loads and stores through such selects are now split per pointer, so the array stays in registers, and the i07 rewrite leaves alone any array that something other than loads and stores reaches. (i17)
- `get_num_samples()` returns 1 in a fragment function that takes a buffer argument, at any sample count. ANGLE's alpha-to-coverage emulation picks its pattern by sample count, so coverage jumped around instead of following alpha. Calls become the pipeline's sample count, which the module carries. dEQP `multisample.fbo_*` and `oes-sample-variables` now pass in Chrome. (i10)
- In a long fragment function, a vector built from immediates and per-pixel values (`FragColor = vec4(1.0, a, b, 1.0)`) gets the immediates right in only one pixel of eight. In the case I disassembled, the back end runs short of registers and reloads the fragment input's interpolation coefficients, then fills the vector's 1.0 lanes from them as if they were a per-pixel value: only the lane holding the constant coefficient reads 1.0. Haswell only: those lanes are computed per pixel in the IGIL text. dEQP `uniformbuffers` `single_struct_array` and `single_nested_struct_array` now pass in Chrome. (i11)
- The back end builds a SIMD8 and a SIMD16 kernel for each fragment function. Under the SIMD16 kernel's higher register pressure, its register allocator can give a compare whose result is only used through the flag a register that still holds a live value; the compare overwrites it. In dEQP's `multi_nested_struct` instance-array case, a bool kept in a register for the last check is overwritten that way: wrong in every SIMD16 dispatch, right in SIMD8 ones. The adapter now hooks iCBE's `CompilePixelShaderOpenGL`, looks for that pattern in the SIMD16 kernel (a flag-writing instruction overwriting a value nothing has read yet, read again afterwards), and if it's there compiles the shader again SIMD8-only. In Chrome's uniform-block pages that was 3 of 220 fragment shaders. dEQP `uniformbuffers` `multi_nested_struct` and `random` now pass. Haswell only. (i14)
- Fine derivatives. MSL has one `dfdx` / `dfdy`, which Apple GPUs evaluate fine (each row or column of a 2x2 quad gets its own difference), and WGSL's `dpdxFine`, `dpdyFine` and `fwidthFine` compile to it. The IGIL back end writes them as `GRADIENT_X` / `GRADIENT_Y`, which the Intel compiler evaluates coarse, so fine derivatives were wrong wherever the rows differ (WebGPU CTS: 8 of 8 cases each). The IGIL text now asks for `GRADIENT_X_FINE` / `GRADIENT_Y_FINE`, which that compiler also reads. Haswell only. (i15)
- A buffer viewed as different types (WGSL's `bufferArrayView`: Tint casts one byte pointer to each view's element type): the back end reorders or forwards an access of one type past an access of the other to the same address, so "load int, store vec2f there, load int" returned the first value (WebGPU CTS `bufferArrayView` `mixed_types_aliasing`, 285 cases, storage and workgroup buffers). Loads and stores through such casts are made volatile, and so is a whole-buffer copy (memcpy) of a buffer that is also viewed that way; `bufferArrayView` now passes 1692 of 1692 and `bufferView` 1206 of 1206. A cast that only feeds such a copy doesn't count as a view: a buffer copied whole into a private variable (Tint's `var v = input;`) has nothing to keep in order, and making that copy volatile lost the values (`memory_layout` `read_layout` with `mat2x2<f16>` arrays, found by a full sweep). (i16)
- The same back end lowers an aggregate copy of a buffer (llvm.memcpy; Tint writes `output.a = *bufferView<array<i32, 32>>(&A, 0)` that way) to loads and reuses an earlier load of a word instead of reading it again after a store through a view, so "load `*p`, store `*p`, copy the buffer out" copied the value from before the store. With constant offsets the front end merges both views into one pointer of one type, so the rule above didn't fire (WebGPU CTS `bufferView` `mixed_types_aliasing`, 96 cases, workgroup and storage buffers). A buffer that is both copied and viewed through a cast now counts as punned: its view accesses and its copies are made volatile. `bufferView` passes 1206 of 1206. (i18)
- Shaders made of chains of short `&&` tests that share an else take exponential time in the back end's register allocator: 4 tests over vec4s compile in 2 s, 6 in more than a minute, 8 in more than ten. Chrome's watchdog kills the GPU process meanwhile. Short blocks that only compute are folded into their predecessor, with the branch conditions combined. Short if/else arms become selects. Functions with fewer than 12 conditional branches are left alone. WebGPU CTS `shader,execution,robust_access_vertex` now runs in 20 s instead of taking WebGPU down. (i12) Folding a block that ends in a `switch` into its predecessor gave the phis of a block that two of the switch's cases go to one entry instead of two, and the IR verifier aborted the compiler (`mslfuzz2` VEC seed 2642; the stock compiler is right): the entries now stay one per case. (i53)
- In indexed draws through an indirect buffer, `[[vertex_id]]` leaves out the base vertex unless the vertex function also reads `[[base_vertex]]`; direct draws are right. Reading it makes the shader declare `BASE_VERTEX_ID` among its system-value constants, and the driver then sets up indirect draws so the hardware vertex ID includes it. Vertex shaders that read the vertex ID get that declaration added. WebGPU's `drawIndexedIndirect` with a base vertex drew from the wrong vertices wherever Dawn's shaders use the vertex index. WebGPU CTS `api,operation,rendering,draw` and `shader,execution,robust_access_vertex` now pass in Chrome. Haswell only. (i13)
- `as_type<uchar4>(ushort2)` and `as_type<char4>(short2)` in vertex and fragment functions: the back end has no lowering for that bitcast (`<2 x i16>` to `<4 x i8>`) there ("IGILTargetLowering::ReplaceNodeResults(): need to lower this!" on a `v4i8` node), so the compiler service crashed and the pipeline failed with "Compiler encountered an internal error". Compute functions, and the other casts between words and vectors of bytes or halfwords, are right. Found by fuzzing fragment functions. In modules with a vertex or fragment function, the cast is built from its bytes instead: each byte a truncation of its halfword lane, shifted right by 8 for the odd ones. (i62)
- Saturating adds and subtracts whose operands become constant only when the Intel compiler unrolls a loop: the back end folds `addsat` / `subsat` of two constants as a plain add / subtract (the fold for constants in the source is above), and in a loop with a constant trip count `addsat(i, ...)` has constant operands in every unrolled copy of the body. Signed `addsat` and `subsat` came out unsaturated, and an unsigned `addsat` picking a private array element (`p[addsat(i, -i) & 7]`) made another value read in the same iteration take its next value (231 of 256 threads, compute and fragment functions). Found by fuzzing fragment functions. The 32-bit `addsat` calls and signed `subsat` calls left after that fold are written out as an add or subtract, compares and selects, which LLVM folds exactly. That also covers i48's and i56's cases, so their "without the fix" runs switch it off too. (i63)
- Compares and selects of `uchar4` / `char4` in vertex and fragment functions: the back end's type legalization of a compare between two byte vectors depends on how each was made. `any(uchar4(a, b, c, d) <= as_type<uchar4>(x))` crashed the compiler service (`SelectionDAG::getZeroExtendInReg`), `any(as_type<char4>(x) > as_type<char4>(y))` came out wrong, and a per-lane `select` of byte vectors by such a compare crashed, also on the bytes i62 builds. Compute functions are right. Found by fuzzing fragment functions. Such compares and selects are done on 32-bit lanes: vectors put together lane by lane are extended lane by lane, other operands are taken apart from their packed word with shifts (sign-extending for signed compares), and a select's result is truncated back. (i64)
- Signed compares of a sum with zero in vertex and fragment functions: iCBE folds the constant of an add into the compare as if the add couldn't overflow, `(x + C) < 0` into `x < -C` (read off the EU code) and `(x + C) > 0` likewise, but MSL's unsigned add wraps, so where `x + C` wrapped past the sign bit the compare went the wrong way: in `if (c) v += (int)(x + 902107310u) < 0 ? y % 1000 : 777u` the pixels whose `x` was in `[2^31 - C, 2^31)` got 777. Compute functions are right. Found by fuzzing fragment functions. In pixel and vertex shaders such compares (`ICMP.lt` / `ge` / `gt` / `le` of an `IADD` result and zero) become tests of the sum's sign bit and, for `> 0` and `<= 0`, of the sum being zero. (i65)
- Arithmetic and bitwise operations on byte and halfword vectors (`uchar4`, `char4`, `ushort2`, `short2`, ...) in vertex and fragment functions: on vectors made with `as_type` (`as_type<uchar4>(x) ^ as_type<uchar4>(y)`, `as_type<char4>(x) | select(...)`) they crashed the compiler service in the same type legalization as the compares above. They are done on 32-bit lanes now as well. Each such operation keeps one 32-bit value per lane, which the operations, selects and compares that use it take directly (masked or sign-extended where the high bits matter), so a chain of them, also one carried around a loop, never goes back through a byte vector. Vectors that aren't 16 or 32 bits wide (`ushort3`, `ushort4`, `uchar3`) are taken lane by lane: `as_type<ushort3>(half3) & 0x7FFF` crashed the compiler too, and RenderBox (SwiftUI's renderer) does exactly that in its resolve shaders, so some of their variants didn't compile on the Iris Pro. WebGL and WebGPU shaders have no 8-bit types. (i66, i69)
- 64-bit integer division and remainder, and 64-bit shifts by a variable amount, in vertex and fragment functions: the compiler service crashed (`((ulong)x << 32 | y) / (ulong)(x | 1u)`, `a >> (y & 63u)`) and the pipeline failed with "Compiler encountered an internal error". Compute functions are right, and so are 64-bit add, multiply, compares and shifts by a constant. Each such operation is done on its operands' 32-bit halves: a shift as 32-bit shifts and a select on whether it moves 32 bits or more, a division as a loop of 64 shift-and-subtract steps (signed: on the magnitudes, with the sign put back afterwards). Fragment fuzzing with 64-bit values crashed on every kernel; WebGL and WebGPU have no 64-bit integers. (i67)
- Branches on a compare of a 0/1 value with 1 in vertex and fragment functions: in `if (((x & 1u) & y) != 1u) { ... }` the back end takes the `& 1` out as redundant for the compare and then tests the whole register (IGIL: `AND r, x, y; IF_CND.z r`), so every pixel where `x & y` has a higher bit set takes the wrong branch: 191 of 256 pixels in i68 with stock OCLP. Compares with 0 and selects are right, so such a compare with 1 becomes the equivalent compare with 0. Fragment fuzzing found it through a `char2` expression that the front end folds to scalars, which is why I first listed it under byte vectors. (i68)
- Ivy Bridge: the same weak load command goes into the `11.7.10` and `11.7.10-22` plugin, a different build of the same compiler. The IR fixes apply there; the IGIL hooks don't match it, so texture atomics and the fixes made in the IGIL text (i11, i13, i15, i24, i29, i30, i32, i37, i40, i41, i45, i46, i48, i52, i54, i55, i57, i60, i61) stay off, the uniformity-analysis hook (i49) only goes into Haswell's libIGIL-Metal, and the SIMD16 check (i14) only looks at Haswell's iCBE. Compile-tested only (`Tests/ivb-compile.sh`), with no Ivy Bridge Mac to run it on: every pipeline in the tests that the stock Ivy Bridge compiler builds also builds with the adapter, and 7 that crash it build.

## 5. `AMDBronzeCompat.dylib`

Weak-loaded by AMDMTLBronzeDriver (`12.5`, `12.5-24`, `12.5-25`, `12.5-GCN-SKL-*`), so in every process using the driver, including on AMD-only Macs and Tahoe, where the Metal wrapper and item 1 don't load. Source: `BronzeCompat/BronzeCompat.m`. Based on riptidewave93's bronzefix.
- Stencil through texture views of mip 1+. The driver's view init counts the view's first level twice in the stencil-plane index, so the write lands on level 0 / slice 0. (s17)
- sRGB mipmaps: the driver's blit averages the encoded bytes, so levels below 0 come out too dark. (s12)
- Blends linearly between mip levels. The 12.5 driver sets `PERF_MIP` in every sampler, so trilinear filtering reads a single level near whole levels and blends only in between (level 0.25 returns 0.19 of the way to the next level). Apple's GPUs blend linearly, and EEVEE samples its depth pyramid just above whole levels: light from bright emitters went missing on nearby surfaces. It costs up to ~12% in a kernel that does nothing but sample textures; Blender's render times didn't change. `MTLSHIM_EXACT_TRILINEAR=0` turns it off. (s19)

- sRGB MSAA resolve: the driver averages the encoded bytes, so antialiased edges come out too dark. These attachments now get resolved in a shader. On `12.5-24` that shader read needs item 2's FMASK fix (riptidewave93), without which it resets the GPU. (s25)
- Depth or stencil copied to a buffer with row pitch 0, which wgpu passes for a single row: the driver writes nothing for one aspect of a combined depth/stencil texture. (s26)
- WebKit's one-vertex pipelines. For a draw of one vertex, WebKit copies the pipeline with the stride set to the end of the last attribute, 2 for `snorm8x2`. The driver refuses a stride that isn't a multiple of 4, WebKit then draws with no pipeline set, and the driver crashes, taking Safari's GPU process with it. In WebKit's processes the stride goes up to the next multiple of 4. (s29)
- WebKit's sample mask of 0. The driver takes it to mean no mask and draws every sample, where nothing should be drawn. In WebKit's processes it becomes a bit past the last sample of any target. WebGPU CTS `occlusionQuery` `sample_mask`: 16 failures to none. (s30)
- Memoryless textures, from riptidewave93. Only Apple GPUs have that storage, and Metal's descriptor validation aborts on it from the driver's texture init. Item 1 prevents that only where it loads, so GCN-only Macs on Tahoe still aborted. The driver now gets a copy of the descriptor with private storage, and `AMD_BRONZE_MEMORYLESS=0` turns that off. Heap, buffer and IOSurface textures with memoryless still abort, as on any non-Apple GPU. (s27)
- MSL 3.2 device coherence on buffers, from riptidewave93. With native Metal (GCN-only Macs), MSL 3.2 compiles, but the driver's compiler fails any buffer with device coherence when the pipeline is made. SPIRV-Cross emits `coherent device T *` for every Vulkan `Coherent` storage buffer, so MoltenVK couldn't create those pipelines (`VK_ERROR_INITIALIZATION_FAILED`). In MSL 3.2+ source compiled on this driver, `coherent(device)` and `coherent device` become `volatile`, as item 1 does on MetalOld (coherence is Apple silicon only). Coherent textures and threadgroup coherence compile and are left alone. (s09)

## 6. Tahoe's compiler for the Metal 3802 stack: 14.2 Beta 1 instead of 13.x

The 13.x front end stops at MSL 3.0, so MSL 3.1 texture atomics don't compile from source there (a01). `tools/make_tahoe_compiler.py` builds it from the `14.2 Beta 1` payload the Sequoia patches use. Paths go from `Versions/32023` to `Versions/31001`, because Tahoe's native compiler lives at 32023 and MetalOld and MTLCompilerService load 31001. The `libLLVM` wrapper and `libLLVM_helper` stay on top, so Tahoe's AIR 2.8 shader libraries still get converted. The files replace the 13.x ones in `13.6-25` and `13.2.1-25`, so `metal_3802.py` needs no change for now. That adds about 100 MB, and `libmetal_boundscheck.a` stays the 13.x one because the `14.2 Beta 1` payload has none.

## 7. Haswell's framebuffer: Linux's RC6 thresholds

`AppleIntelFramebufferAzul.kext/Contents/Info.plist`, `RCxControl`, in `Universal-Binaries/12.5`, `12.5-23` and `12.5-23.4`. The Monterey framebuffer OCLP installs for Haswell programs the GPU's RC6 (render standby) timers from `RC6_Threshold` 520 and `RC_Eval_Interval` 26000, in 1.28 µs units (registers 0xA0B8 and 0xA0A8), so the render engine enters RC6 far sooner than under Linux (below). On the Iris Pro 5200, Safari's WebGL video uploads (bursts of small submissions from ANGLE, CoreImageOld and video decoding in one GPU process) hung the GPU on its way out of RC6. All 8 Intel GPU Hang Summaries I collected look the same: the render ring is "hung in the ring" at the first command of the next submission, the last instruction it parsed is `3DSTATE_VF` (the end of a render-context restore), the media, blitter and video-enhancement rings wait on the semaphores the render ring signals after every batch, and every ring has sleep messages enabled (`RC_PSMI_CTRL` 0x10). That's the gen7 hang Linux works around in 2c550183 ("drm/i915: Disable PSMI sleep messages on all rings around context switches"), and Linux programs RC6 far less eagerly on Haswell: `GEN6_RC6_THRESHOLD` 50000 in a `GEN6_RC_EVALUATION_INTERVAL` of 125000. Those are the values here. Once, WindowServer didn't survive the GPU restart, and watchdogd panicked the Mac. With RC6 turned off (`RenderStandby` 0) or with these values, the video pages run without a GPU reset (11,4 results); these values keep RC6 for an idle GPU. OCLP copies this `Info.plist` as it is apart from `OSBundleRequired`, so nothing else needs to change.

## Known limitations

- Metal's validation layers don't run on this stack (item 41 switches them off): API and shader validation need the OS's own Metal runtime and compiler.

- The 14.2 compiler on Tahoe is untested on Ivy Bridge and Kepler, and I don't know why Tahoe started on 13.x; I've asked in the comments. A few MPS kernels crash the compiler service on the R9 M370X: one crash (in `libAMDIL902`) also happens on 13.x, another (in `libSC`) I've only seen on 14.2.
- Safari's WebGPU can't be tested on Sequoia: Apple keeps it off there (`navigator.gpu` is absent, and I found no setting that turns it on). So s28 runs only on Tahoe, and on Sequoia Safari's fixes were only checked through WebGL.
- The memoryless hook in item 5 came after all the installed runs above. On this Mac, `verify.sh` runs it on the `12.5` payload: s27 aborts without it and passes with it, also with item 1's own fix off. riptidewave93 tested it in test processes on Tahoe.
- Intel-only Macs have been tested on one MacBookPro11,4 (Iris Pro), on Sequoia only (results above). Ivy Bridge has only been compile-tested.
- Safari on the Iris Pro loses WebGL until it restarts after a 16384x16384 canvas (11,4 results above).
- The portrait blur itself (`CIDepthBlurEffect`, Photos' portrait editing) isn't applied: `CoreImageOld` builds it from stitchable functions in Sequoia's `CIPortraitBlur*.metallib`, and neither the Iris Pro nor the R9 M370X has function pointers, so the filter returns its input (it used to crash; s53).
- Shadow lookups with a bias lose the bias on Intel (i03), because that compiler can't compute an LOD; it only matters for mipmapped shadow maps.
- c04 hasn't run on an installed Tahoe. The compiler can't run inside a test process there (below), so it should report SKIP.
- A struct that points to itself (`struct L { device L *next; int v; }`) still leaves an entry in the map patch 5 fixes, because the objects keep each other alive and are never destroyed. The memory stays valid, so it can't crash the way patch 5's case did. 300 kernels with different layouts, each writing through its struct on the GPU, gave no crash and no wrong write, with 63 entries left at the end. A later compile whose metadata lands on such an address could in principle read the old layout. I haven't seen that.
- Stencil8 textures read wrong beyond slice 0 of level 0 (blits are right), in Safari and Firefox; Chrome avoids it by using a combined format. The T# layout looks wrong; a fix would mean remapping Stencil8 to a combined format in the driver.
- With the 14.2 compiler installed on Tahoe, `verify.sh` isn't usable: 10 tests abort in `deserializeArguments` with the GPU compiler in-process, with and without the fixes. `run.sh` on the installed system works.
- During this testing, a Tahoe run with the 13.x compiler ended in a GPU reset loop in Firefox while my compiler experiments ran alongside it. It hasn't come back on 14.2 with Firefox running alone, and I don't know the cause.
- Mostly tested on one MacBookPro11,5. A second MacBookPro11,5 confirmed Chrome on Sequoia, and a MacPro6,1 on Tahoe the compiler fixes and `AMDBronzeCompat`, including s25 and s26. The GCN 1.0 fixes check the GPU family and do nothing on other GPUs; the rest should apply to every GCN card on this stack, but I haven't seen it run there. riptidewave93 ran `AMDBronzeCompat.dylib` and the FMASK fix (a11) on `12.5-24` on a GCN-only MacPro6,1 with Sequoia, installed system-wide: clean login, no GPU resets, Safari's WebGL cube renders.
- Intel still fails to compile shaders that pick a texture with a select (`cond ? &t[1] : &t[0]`). Native macOS 12 does the same, and ANGLE doesn't generate that shape.
- The large kernel with many `mulhi` / `madhi` calls that crashed the Intel back end with i21 (`mslfuzz2` LONG seed 71) compiles and is right since the later constant folding. The fuzzers' other open Intel findings, LONG seed 6 and plain seed 565, are fixed (i40, i41). The narrow-vector mode's seed 1568, a back-end bug the stock compiler shares, is fixed too (i48), and so is LONG seed 741, which crashed the stock compiler's uniformity analysis (i49).
- Apps using WKWebView get the system WebKit from the shared cache. The shim now reaches that copy (it's what Safari uses on Tahoe), but I haven't tested a WKWebView app.
- The Intel compiler folds float arithmetic on constant subnormals as if they were normal numbers with exponent -127 ((1 + mantissa) x 2^-127): `dot(float2(9, 1.4e-45), float2(-15, FLT_MAX))` from a constant table came out -133 instead of -135 (WebGPU CTS `f32_matrix_vector_multiplication` `vector_matrix_compound` with constant inputs, 1 case). Runtime subnormals are flushed to zero, which is allowed. Only constant tables with subnormal values reach it, so it isn't worked around.
- Still wrong on the 12.x Intel driver, with no fix here: points can't be bigger than 256 pixels (the hardware's limit is 255.875), though ANGLE reports 511; there are no indirect command buffers (`newIndirectCommandBufferWithDescriptor:` returns nil); fragment functions with about 160 live vec4s fail to compile.
- Sequoia's Metal Performance Shaders has no NDArray matrix multiply kernel for these GPUs (Mac1 family): `MPSNDArrayMatrixMultiplication`, and through it MPSGraph's matmul, encode nothing for 16x16 and larger, so the result stays 0. The classic `MPSMatrixMultiplication` is right at every size. Vision's image classifier on the GPU doesn't go through it and is right.
