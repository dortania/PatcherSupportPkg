# Legacy Metal fixes: what each one does

The fixes in this folder, grouped by the file they ship in, with the bug each one works around, how it was found and
the test that shows it (`Tests/`, run by `verify.sh` without and with the fix):

- `sNN`: `MetalOldCompat.dylib` (Metal framework level) and `AMDBronzeCompat.dylib` (12.5 AMD driver)
- `aNN`: `AMDTextureAtomics.dylib` (12.5 AMD shader compiler)
- `cNN`: the libAMDIL902 patches
- `iNN`: `IntelTextureAtomics.dylib` (3802 Intel shader compiler)
- `rNN`: guards that keep a fix from regressing

Most fixes can be switched off for a test with an environment variable (`MTLSHIM_*`, `AMD_*_FIX`, `INTEL_*_FIX`), named
in the source next to each one.

## 1. `MetalOldCompat.dylib`

Loaded by the Metal.framework wrapper in `13.2.1-24` and `13.2.1-25` (Tahoe), so in every Metal app. Source: `MetalOldCompat/MetalOldCompat.m`.
- Adds the macOS 13.3-15 Metal methods MetalOld lacks. Chrome calls `setMathMode:` on every shader compile and aborts without it. (s01, s08)
- Makes reflection data from the newer compiler readable (s02), accepts `MTLTextureUsageShaderAtomic` (s03), and converts vertex-descriptor layout records between the two formats (s07).
- Accepts MSL 3.2 requests, which Firefox's WebGPU and MoltenVK make on Sequoia. (s09)
- Fixes a device over-release crash in MetalOld's device list that killed Chrome's GPU process. (s10)
- Lets ANGLE (Chrome, Safari, Electron, and Firefox, whose WebGL on macOS runs on its own ANGLE build, `libGLESv2.dylib`, from Firefox 160 (159 used OpenGL): it had no WebGL at all on these Macs, "FEATURE_FAILURE_NO_DISPLAY"; s64. Any app that bundles ANGLE under that name is treated the same) past its Mac-model check and gives it the GPU that can run WebGL here, the AMD card (family 2). On Macs whose only GPU is the Intel one (family 1), ANGLE refuses it, so there it's presented to ANGLE as family 2. ANGLE's own fallbacks are switched on, through `ANGLE_FEATURE_OVERRIDES_DISABLED`, for the three family-2 features the Intel driver lacks (swizzled texture views, stencil MSAA resolves, pipelines without attachments) and for depth comparisons with gradients, which the Intel compiler can't build. Dawn (Chrome's WebGPU) hears the same family-2 answer, except for two questions that get the real one: whether to offer subgroups (the Intel compiler can't build SIMD-group reductions, and the compiler service aborts) and whether to offer texture-component-swizzle (no swizzled views). The shim recognises both by the order and closeness of Dawn's family checks; ANGLE's checks still get family 2. (s31; `chrome://gpu` shows the rest) On Kepler (GTX 600/700) ANGLE also refuses the GPU by vendor (its `disableMetalOnNvidia` feature: "the Metal display didn't initialize", no WebGL in Firefox or Safari); that feature is overridden with the others, and Kepler passes s63 and s64 with it. ANGLE also turns its shared-event fences off on NVIDIA (`hasEvents`, crbug.com/1136673), which takes `GL_ARB_sync` away, and Safari 18's WebKit requires that extension for every WebGL context: on Kepler every WebGL and WebGL 2 context in Safari was created already lost (CONTEXT_LOST_WEBGL), with nothing logged. Kepler's shared events and ANGLE's fences on them work on this stack (hundreds of fence waits and polls, none timed out), so when WebKit is the caller `hasEvents` goes on `ANGLE_FEATURE_OVERRIDES_ENABLED`; Chrome and Firefox keep ANGLE's choice (s69; `MTLSHIM_ANGLE_EVENTS=0` turns it off).
- Works around Intel driver bugs: MSAA resolves (s15a), narrow clears (s15b), 2D-array views (s16), 8-byte buffer fills (s20), depth-only pipelines (s21), HiZ on depth textures with several levels or slices (s22), 3D mip planes (s23), R8/RG8 clears at mip 1+, and BGRA8 clears at mip 2+ that don't start on a 16-texel column of the mip layout (level 1's width rounded up to 4 not a multiple of 16: base widths 8-24, 40-56, 80, 100...; nothing landed there, while RGBA8, blits and draws were right) (s24), and depth and stencil written by blits, which later render passes didn't see (s32). ANGLE copies stencil that way on Intel GPUs, so `glBlitFramebuffer` lost it. More Intel driver workarounds follow below.
- Applies the Kepler fixes below on all Kepler GPUs. The driver has each encoder class twice, once per 3D class, with the same code: `_KEPLER_A` for the GK104, GK106 and GK107 (the GTX 770 these were found on, and most GTX 600 / 700 cards) and `_KEPLER_B` for the GK110 and GK208 (GTX 780 and Titan, GT 710 / 720 / 730), with `_KEPLER_COMPUTE_A` / `_B` likewise. The fixes hooked only the `_A` classes, so they did nothing on a GK110 or GK208, and item 62's hidden buffer, which the compiler adapter adds to every ANGLE function that samples a texture, wasn't bound there. Every hook now goes on both, each calling the original of its receiver's class (`keplerSwizzle`). The `_B` copies were compared instruction for instruction with the `_A` ones; there is no GK110 or GK208 here to run them on.
- Works around a Kepler driver bug (GeForceMTLDriver, GTX 770): a small stencil upload (a copy from a buffer into Stencil8 or into a depth/stencil texture's stencil, up to 16 KB) isn't ordered before the blit encoder's next command, so copying it back out right after read zeros in 10% to 83% of runs. A 4-byte fill of a scratch buffer after each stencil upload orders it; `MTLSHIM_NV_STENCIL_ORDER=0` turns it off. (item 53, s62)
- Adds two methods the Kepler driver lacks, whose calls threw "unrecognized selector" and aborted the process. Swizzled texture views (`newTextureViewWithPixelFormat:textureType:levels:slices:swizzle:` on `NVMTLTexture`): Kepler is family 1, but item 11 makes a lone family-1 GPU family 2 for Chromium, and Dawn makes its depth/stencil views with the swizzle (R, 0, 0, 1). As on Intel (item 32), a swizzle that changes nothing a shader can see makes the view without it; any other returns nil. Indirect command buffers (`newIndirectCommandBufferWithDescriptor:maxCount:options:` on `NVMTLDevice`, which MetalOld calls for every driver): Kepler isn't Mac2, so nil, as for other GPUs without them. `MTLSHIM_KEPLER_METHODS=0` turns it off. (item 54, s36, s42, s54)
- Works around a Kepler driver bug: an MSAA resolve into mip level 1 or higher never arrived after a pass that draws (any slice, linear and sRGB alike; level 0 and clear-only passes are right). As on Intel (item 15), such a resolve goes into a temporary texture of the level's size, copied to the level when the encoder ends. `MTLSHIM_NV_RESOLVE_LEVEL=0` turns it off. (item 55, s25)
- Works around a Kepler driver bug: a view made from a texture view of levels 1+ and slices 1+ lost the first view's offset (a stencil view of a depth-stencil view read the wrong level and slice; Dawn reads WebGPU's stencil8 that way). Views of views are made from the root texture with the offsets added, as Metal defines them. `MTLSHIM_NV_VIEW_OF_VIEW=0` turns it off. (item 56, s46)
- Works around MPSGraph's softmax on Kepler: over any axis but the last it came out wrong (axis 0 of a 2D tensor wrote one element and left the rest 0; axes 0 and 1 of a 3D one were wrong everywhere), while over the last axis it's right. Built from its parts in one graph, MPSGraph fuses them back into the same kernels, so such a softmax is done over the last axis between two transposes. `MTLSHIM_MPSGRAPH_SOFTMAX=0` turns it off. (item 57, i71)
- Makes MSL 3.1 texture atomics work on Kepler. Its back end has no texture atomics the compiler can emit, and its library no body for them, so a kernel or fragment function with `atomic_fetch_add` and the rest on a texture crashed the compiler (a01; Blender assumes texture atomics on every macOS 14+ Mac). Kepler can do them as global atomics if the texels are in a buffer, and its driver makes linear textures from buffers (2D only). So an R32Uint / R32Sint 2D texture of one level, one sample and no render-target use that is created with `MTLTextureUsageShaderAtomic` (what Metal asks of a texture for atomics) is made a linear texture in a buffer of its own, after a 256-byte header (a magic number, the row pitch, the size; written by a blit for private storage). The Kepler adapter (section 8) turns each texture atomic into a global atomic on a hidden buffer parameter, and the shim binds the texture's buffer there before each draw or dispatch, finding the index from the pipeline's reflection the same way the adapter picks it (each read_write `texture2d<uint>` / `<int>` argument in order, counted down from 30 over the buffer indices the function doesn't use), and puts back whatever the app had bound there afterwards. Another texture at that argument (a tiled one) gets a dummy buffer without the header, and its atomics do nothing, as do coordinates outside the texture: they land on a word of the header instead of on another buffer. The encoders track their bindings only once a pipeline with such an argument exists, so other apps pay about 1 ns a bind call. 2D arrays, 3D and 1D textures have no linear form on Kepler, and textures from heaps aren't covered. `MTLSHIM_NV_TEXTURE_ATOMICS=0` turns it off. (item 58, a01 and n04)
- Sums visibility results on Kepler. Its driver writes each draw's own sample count to the visibility slot, replacing what the slot held, so a slot ended with the last draw's count, not the sum over the pass's draws that Metal specifies, and WebGL occlusion queries in Chrome reported visible targets invisible (Khronos WebGL 2.0.1 deqp `occlusionquery_strict` / `_conservative`: two target draws per query, the second hidden). A render pass with a visibility result buffer gets a private one of the shim's: while a mode is set, every draw gets a slot of its own, and when the encoder ends a compute pass on the same command buffer writes each app slot the sum of its draws. A slot a mode was set on without any draw gets 0, as Metal specifies; the driver left it as it was (WebGPU CTS `occlusionQuery` `empty`, `initial`). Item 59, `MTLSHIM_NV_VISIBILITY_SUM=0`. (n08)
- Zero-fills new private buffers on Kepler. Its driver hands a freed private buffer's memory, as it was, to the next private buffer of the same size (a fresh 1 MB buffer read all 0xAB after one filled with 0xAB was released), and does the same with a counter sample buffer's result buffer (unsampled timestamp slots resolved to a freed buffer's timestamps). Metal documents new buffers as zero-filled and Dawn relies on it, so WebGPU read old values from unused query slots (WebGPU CTS `timestampQuery` `unused_slots_are_zero`), and a WebGPU buffer could show data the page had freed. Each new private buffer, and each new sample buffer's result buffer, is filled with zeros by a blit on a queue of the shim's, waited for before it is returned (0.2-0.3 ms a buffer). Heap buffers keep their undefined contents, as Metal specifies. `MTLSHIM_NV_ZERO_BUFFERS=0` turns it off. (item 60, n09)
- Makes counter resolves on Kepler safe. Its driver's `resolveCounters:inRange:destinationBuffer:destinationOffset:` reads the sample buffer's own result buffer without putting it in the command buffer's resources, so nothing makes it resident, and when its pages weren't mapped the GPU faulted (kernel log: `Access Violation Error (MMU Error 2)`, `FAULT_PTE`) and the driver killed the context: the next command buffer failed with `InvalidResource` and Chrome lost its WebGPU device (WebGPU CTS `timestampQuery` `resolve_unused_slots`). Whether a process faults depends on its allocations; no small program was found that does. Each resolve first copies 4 bytes of the result buffer to a small buffer of the shim's in the same encoder. `MTLSHIM_NV_RESOLVE_RESIDENCY=0` turns it off. (item 61; reproducer: a WebGPU page resolving two 4096-slot timestamp query sets, then copying in another submit)
- Gives depth and stencil textures sampled through `texture2d` the channels OpenGL ES wants, in ANGLE's shaders on Kepler. Its sampler returns a depth texture's depth in all four channels, (d, d, d, d), and a stencil view's value as (s, s, s, s), where OpenGL ES wants (d, 0, 0, 1) / (s, 0, 0, 1); Metal leaves those channels undefined, and ANGLE puts them right with swizzled views, which it only makes on GPU family Mac2 (this driver's come out empty): WebGL's depth texture tests failed in Chrome and Firefox (Khronos WebGL 2.0.1 depth texture formats, `fboinvalidate` `unbind_read_*`, about 12 pages). In ANGLE's vertex and fragment functions (the ones with an `ANGLE_angleUniforms` argument), the Kepler adapter (section 8) makes each sample or read of a texture argument (x, 0, 0, 1) when bit n of a mask at a hidden buffer index is set; the index (the next free one counted down from 30, after item 58's) is worked out here from the pipeline's reflection the same way, and before each draw the mask gets a bit for each depth or stencil texture bound (item 58's tracking). The two halves must agree: a fragment function whose hidden buffer isn't bound draws nothing on this driver. `MTLSHIM_NV_DEPTH_CHANNELS=0` turns the shim's half off (with `NVAIR_DEPTH_CHANNELS=0` for the adapter's). (item 62, n11)
- Copies 3D textures on Kepler with the image stride they ask for. Its driver read or wrote slice n of a copy between a buffer and several slices of a 3D texture at n x bytesPerRow x height, ignoring a larger bytesPerImage (WebGPU's rowsPerImage above the copy height), so those slices came from or landed in the padding (WebGPU CTS `image_copy` `rowsPerImage_and_bytesPerRow`: 114 cases, all 3D). Such copies are done a slice at a time. `MTLSHIM_NV_VOLUME_COPY=0` turns it off. (item 65, n15)
- Counts occlusion-query samples on Kepler for draws that write no color. Its driver counted none for a draw whose color attachments all have writeMask none and that has no depth or stencil attachment, so a visible draw read as hidden (WebGPU CTS `occlusionQuery` `basic`, `reuse` and `scissor` with writeMask 0). Such pipelines write their first blendable attachment through a blend that keeps it, as item 34 does on Intel. `MTLSHIM_NV_MASKED_DRAWS=0` turns it off. (item 66, n16)
- Uploads into the last row of blocks of a block-compressed texture on Kepler. Its driver wrote nothing for a copy from a buffer into a BC texture that ends at the level's bottom edge with a height short of a whole block (the 13x1 edge row of a 13x13 level), as if it rounded the block rows down; edge columns, whole levels and copies out were right (WebGPU CTS `image_copy` `compressed_textures,unaligned_mip_level_0`, every BC format). Such a copy's height is rounded up to the block, which the level's memory holds. `MTLSHIM_NV_BLOCK_EDGE=0` turns it off. (item 67, n17)
- Rasterizes triangles across the edge of the viewport whole on Kepler. Its driver sets the viewport clip control (method 0x193c) with bit 7, which makes the geometry guard band the viewport itself: a triangle crossing the viewport's edge was clipped there and the polygon left drawn as a fan of triangles, so with multisampling each pixel on a seam of the fan ran the fragment function once per part, each time with only that part's samples in `[[sample_mask]]` (WebGPU CTS `fragment_builtins` `inputs,sample_mask`: 7, then 8, for a pixel whose 4 samples are all covered, in every case with an edge of the triangle inside the target; the R9 passes them all), and a fragment function's writes and atomics happened twice there (the usual full-screen triangle (-1,-1), (3,-1), (-1,3) at 4x ran it 20 times for 16 pixels). The bit is cleared, which gives the guard band of 256 times the viewport that nouveau has on this hardware; depth clipping doesn't depend on it, and is unchanged. The value is an immediate in the driver's code (the same instruction pair in 10 places for each of its two forms), patched once the driver is loaded, and only if all 20 are found. `MTLSHIM_NV_GUARD_BAND=0` turns it off. Bit 10 of the same value does it for lines and points: a point whose center was outside the viewport was culled whole, with the part of a wide point that's inside (Khronos WebGL `clipping-wide-points`; nouveau leaves this bit clear too), so it's cleared in the same immediates (`MTLSHIM_NV_POINT_GUARD_BAND=0` keeps it). The driver keeps drawing inside the viewport only through those tight guard bands: the pixel clip rectangle it gives the GPU is the render target (nouveau sets it to the viewport). So with them widened, a triangle or wide point reaching past a viewport smaller than the render target drew outside the viewport (a full-screen triangle through an 8x8 viewport of a 16x16 target: 44 pixels outside; neither conformance suite caught it). The scissor rectangles the driver gets are now the app's intersected with the viewports' (the pixels whose centers are inside, one per viewport), and the driver is only patched when these hooks can be installed too. (item 69, n20, n23, n24)
- Reversed viewport depth ranges on Kepler. A viewport whose znear is above its zfar, which Metal allows ("which you can flip", in `setViewport:`'s documentation) and MoltenVK passes on from Vulkan, wasn't reversed: the driver keeps each viewport's z scale as |zfar - znear| and its translate as min(znear, zfar), so znear 1, zfar 0 stored a z of 0.25 as 0.25 instead of 0.75 (the Iris Pro gets it right; ANGLE reverses WebGL's depth ranges itself, so WebGL wasn't affected). After the driver's `setViewport:` and `setViewports:count:`, such a viewport's scale and translate in the encoder's state become zfar - znear and znear; both setters' code is checked for the stores this relies on. `MTLSHIM_NV_REVERSED_DEPTH=0` turns it off. (item 70, n21)
- Reports Kepler's 2x and 8x sample positions in the hardware's order. Both patterns use the standard positions, in another order than `getDefaultSamplePositions:count:` listed them: at 2x samples 0 and 1 are swapped, and at 8x sample 0 is at (0.0625, 0.4375), which Metal gave as sample 5's (4x is right, and the only count WebGPU uses). Anything matching sample indices to positions, such as a custom resolve or a per-sample technique, got the wrong sample. `NVMTLDevice` gets its own `getDefaultSamplePositions:count:` with the order measured on the GTX 770 (a GK104) for 2 and 8 samples; the GK110 and GK208 are assumed to match, not measured, (the method is only MetalOld's `_MTLDevice`'s, so the other drivers keep it). `MTLSHIM_NV_SAMPLE_POSITIONS=0` turns it off. (item 71, n22)
- Safari:
  - compiles ANGLE's internal shaders from source, because Safari's prebuilt metallib targets macOS 15.4. Safari 18.6 on Sequoia has an older ANGLE whose library (AIR 2.7, `air64-apple-macosx15.8.0`) the old detection missed and whose functions differ, so every antialiased WebGL context failed its multisample resolve and drew nothing (WebGL with `antialias: false` worked). Its library now gets the source of WebKit's matching ANGLE (s63). Sequoia only: Tahoe's compiler reads AIR 2.7;
  - restores the argument encoders that the wrapper stubs out for processes with "Safari" in the path (s14).
- Argument encoders on Ivy Bridge. OCLP's 11.7.10 HD 4000 driver has no argument-buffer layouts or encoders, so asking for an encoder ended in MetalOld's `-[MTLIOAccelDevice newIndirectArgumentEncoderWithLayout:]`, which calls `abort()`. Once the encoders were restored for Safari (s14), its GPU process died at the first WebGL 2 draw with a uniform block, and every WebGL context of the page with it, WebGL 1 included (seen in Safari 18.6 on an HD 4000, where s14 aborted outside the Safari path as well). MetalOld's abort now returns nil, which is what the wrapper's stub gave Safari before. `MTLSHIM_ARGUMENT_ENCODER_GUARD=0` turns it off. (s60)
- Argument buffers on Ivy Bridge. Its compiler doesn't emulate them (the 12.x one turns each pointer member into a hidden constant buffer that its driver binds at the draw) and reads a pointer member as an offset into the argument buffer itself: a kernel read the argument buffer instead of the buffer it pointed to, and a vertex or fragment function that dereferenced one didn't build ("Compilation failed", or the compiler service crashed). So WebGL 2 uniform blocks, which WebKit's ANGLE keeps in an argument buffer, couldn't work at all. The Intel adapter now makes each pointer member a hidden buffer parameter at a buffer index the function doesn't use (counted down from 30; vertex functions keep 0-16 for vertex buffers), and the shim gives the device argument-buffer layouts (the struct's C layout) and encoders, works out each pipeline's hidden indices from its reflection, and before each draw or dispatch binds the buffers the bound argument buffers point to there, putting the app's own bindings back afterwards. Pointers and arrays of pointers are covered, constants stay in the argument buffer; textures and samplers inside argument buffers, nested argument buffers and tessellation draws aren't. `MTLSHIM_IVB_ARGUMENT_BUFFERS=0` and `INTEL_IVB_ARGUMENT_BUFFER_FIX=0` turn the two halves off. (s61)
- Depth blit-copied into a level or slice other than 0 on Ivy Bridge. The HD 4000 driver keeps the hierarchical depth buffer of those levels and slices out of step with what a blit wrote, as the 12.x driver does, so a later render pass failed every depth test against it (s22: level 2). The 12.x fix (creating such textures without HiZ through the device's `bHizDisable`) has no counterpart on this driver, so these textures keep HiZ there and get the rewrite the shim already does for single-level depth textures: when the blit encoder ends, each region is copied out and written again by a render pass, which keeps HiZ in step. Depth32Float_Stencil8 textures are left out, as their render passes already go through a temporary texture (s17). Clears followed by a copy out are right on this driver. (s22)
- Blits at levels 1 and up of mipmapped depth arrays on Ivy Bridge. Any blit that read or wrote level 1 or higher of a Depth16Unorm or Depth32Float 2D-array, cube or cube-array texture with several levels, even 4x4 texels, left bands of the whole texture wrong: rows of other slices were zeroed or overwritten with another level's (one copy out of level 1 of a 2-layer, 3-level 64x64 cube array broke parts of 13 other slices). The copy itself also moved the wrong texels. Shader reads before the blit were right, and blits at level 0 change nothing; the Iris Pro and the R9 get all of it right. Such textures keep HiZ on Ivy Bridge (the item above), and the driver's resolve for a blit at a lower level seems to use a layout of its own, so redoing the copy afterwards isn't enough: these copies no longer reach the driver. When the blit encoder ends, in order with the rewrites above, a compute pass reads the texels with `read()`, and texels for such a level are written by the same render pass as above, from a temporary buffer filled in place. The blit encoder's later commands (copies, buffer copies, fills, synchronizes, fence updates and waits, counter samples, and the other blit commands the driver has) wait too and run after it in order, so a copy of the destination, a `synchronizeResource:` of a managed buffer, or the next encoder waiting for a fence the same encoder updates sees the result. Depth32Float_Stencil8 copies go this way only with `MTLBlitOptionDepthFromDepthStencil`. `MTLSHIM_DEPTH_LEVEL_BLITS=0` turns it off. (s70)
- Depth clears on Ivy Bridge. A render-pass clear of a level above 0 or a slice above 0 of a mipmapped, cube or cube-array depth texture (Depth16Unorm, Depth32Float, Depth32Float_Stencil8) didn't land once that subresource had been written, unless slice 0 was cleared in the same command buffer. A point-light shadow cube whose faces 1-5 were updated without face 0 kept their old depth wherever nothing was drawn, and a mip level 1 likewise; plain 2D textures and single-level 2D arrays were right. And where a clear did land on Depth32Float (and every Depth32Float_Stencil8 slice), it kept about 16 bits of mantissa: 0.05 came back as 0.0499999523 (0, 1, 0.5 and 0.25 were exact). Haswell's driver keeps the same 16 bits on single-level 2D and multisampled 2D Depth32Float and Depth32Float_Stencil8 textures, so that part runs there too (its re-clears all land); the R9 gets both right. Such a pass now starts with a full-screen draw that writes the clear depth exactly (compare always; color and stencil untouched), as draws there are right; the encoder's depth state and viewport are put back. `MTLSHIM_DEPTH_CLEAR_DRAW=0` turns it off. (s71)
- Render passes at levels 1 and up of mipmapped depth arrays and cubes on Ivy Bridge. After any render pass with a depth attachment at level 1 or higher of a Depth16Unorm or Depth32Float 2D-array, cube or cube-array texture with several levels, even one that only loads and stores, fragment shaders sampling level 0 read parts of some other slices wrong: slice 3 of a 57x13x7 array, face 1 of a cube, whichever slice the pass was on. The texels themselves were right (compute reads saw them), and sampling was right again once a pass at level 0 had run; plain 2D textures with mips are fine. The blit fix above writes such levels with render passes, so this showed up once WebKit's ANGLE filled depth arrays and cubes level by level: dEQP `texstorage2d`/`texstorage3d` `format_depth_stencil` (cube and 2D-array cases) and `textureformat` `sized_depth_stencil` failed in Safari. Each such pass is now followed by an empty pass at level 0, slice 0. `MTLSHIM_DEPTH_LEVEL_REPAIR=0` turns it off. (s72)
- Copies between a format and its sRGB variant on Ivy Bridge and Haswell. A texture-to-texture copy between RGBA8Unorm and RGBA8Unorm_sRGB (and back, and BGRA8, BC1, BC3) didn't copy the bytes as Metal says it does: RGBA8 and BGRA8 texels came out color-converted (a 1 became 13, the sRGB encoding of 1/255) and BC blocks garbled, at every level, and the same through a view of the other format, which is how Dawn makes such copies. WebGPU `copyTextureToTexture` between `rgba8unorm` and `rgba8unorm-srgb` (and the bgra8 and BC pairs) failed (CTS `color_textures`, every dimension). The R9 gets them right. Such copies, through views too, now go through a temporary buffer between the root textures. `MTLSHIM_SRGB_COPY=0` turns it off. (s73)
- Blits through texture views on Ivy Bridge. A blit from or into a view (between textures, or with a buffer) ignores the view's offset into its parent and reaches the parent's slice 0 and level 0; shaders reach the right subresource through the same view. ANGLE copies a cube's faces through single-face 2D views when `generateMipmap` gives the texture its mip chain, so in Chrome (and Firefox 160) every face of a mipmapped cube map became +X's (WebGL CTS `texture-size-cube-maps`, 135 checks). Such blits now address the view's parent at the view's slice and level. `MTLSHIM_VIEW_BLITS=0` turns it off. (s65)
- Multisampled depth cleared by a render pass on Ivy Bridge. The clear is a fast clear, and before a later render pass samples the texture the driver resolves only its first width/2 x height/2 texels (single-sample extents on the 4x surface); the rest reads 0. Ahead of a compute dispatch it resolves all of it. ANGLE resolves a multisampled depth renderbuffer for `glBlitFramebuffer` by sampling it in a fragment shader, so cleared depth copied out of one came out as 0 (WebGL CTS `multisampled-depth-renderbuffer-initialization`; three.js resolves the depth of multisampled render targets that way). After a pass that clears a sampleable multisampled depth attachment, a one-thread compute dispatch now reads the texture. `MTLSHIM_MSAA_DEPTH_RESOLVE=0` turns it off. (s66)
- Stencil drawn with a sample mask on Ivy Bridge. When a fragment function writes `[[sample_mask]]` and the render pass has no depth attachment, none of its stencil writes land, at 1x and 4x alike; with a Depth32Float_Stencil8 texture attached as depth as well, they do. ANGLE's fragment functions write the sample mask whenever they render multisampled, and a multisampled `GL_STENCIL_INDEX8` renderbuffer is a stencil-only attachment (Depth32Float_Stencil8 since s40), so the stencil of every draw into one was lost: dEQP `fbomultisample` `stencil_index8` (2, 4 and 8 samples) resolved stencil 0 everywhere, in Chrome, Safari and Firefox. A render pass whose stencil attachment is a combined depth/stencil texture and that has no depth attachment now gets the same texture as its depth attachment, loaded and stored so its depth stays as it was, and its depth/stencil states are swapped for copies that write no depth and compare Always, except Never, which stays: that's what a pass without a depth attachment does on Apple's GPUs (on an M3 Pro, Never rejects every fragment, the other compares pass them, and the depth plane is left alone). `MTLSHIM_STENCIL_WITH_DEPTH=0` turns it off. (s67)
- Direct draws after an indirect draw on Ivy Bridge. Once a render encoder has drawn through an indirect buffer, the HD 4000 driver gives every later direct draw in it that draw's base instance, and, in vertex functions that read `[[vertex_id]]`, its base or start vertex too. Setting the pipeline again doesn't reset it; a new encoder does. MoltenVK and WebGPU mix both kinds of draw in one pass. Indirect draws are right whatever came before, so after the first one in an encoder, the shim sends that encoder's direct draws through a small indirect buffer of its own. `MTLSHIM_IVB_DRAW_PARAMETERS=0` turns it off. (i13)

## 2. `AMDTextureAtomics.dylib`

Weak-loaded by AMDShared (`12.5`, and `12.5-GCN-25` on Tahoe), AMD shader compiles only. Source: `AMDAdapter/`.
- Texture atomics (MSL 3.1), which the 12.5 compiler drops silently. EEVEE's shadows need them. (a01)
- Textures and samplers reached through a pointer stored in memory get a garbage descriptor. WebGL sampler arrays indexed in a loop render black, and one hung the GPU in Chrome. (a05)
- GCN 1.0 (Southern Islands) only; other GPU families are left alone:
  - Missing wait states before scalar buffer loads: wrong uniform values in WebGL 2. (a02)
  - Stale reads right after a write: black blocks behind glass and water in EEVEE. (a03, needs Blender)
  - Threadgroup memory read at the wrong address through a stored pointer: EEVEE depth of field. (a04; r01 guards the fix)
- Compares that must be false for NaN. Metal's fast-math default marks every function `"no-nans-fp-math"="true"`, and the 12.5 compiler's LLVM then compiles `if (x > t)` so that a NaN takes the branch. EEVEE's `safe_normalize()` of 0/0 (the world sun, when the world has no sun) returned NaN instead of its fallback, which zeroed all volume lighting. The adapter sets the attribute to false; the other fast-math options stay. (a06)
- `ldexp` on `half`. libAMDIL902 crashes on `half3` (it widens vec3 intrinsics by name, and has no `air.fast_ldexp.v4f16`) and returns wrong values for the other widths. The adapter computes in `float`, where every `half` is exact. WebGPU CTS `builtin,ldexp:f16`: 12 failures to none. (a07)
- `gather` on integer textures. libAMDIL902 asks `fetch4` for unnormalized coordinates but passes normalized ones, so every call returns the texels at the texture's corner. The adapter switches the IL to normalized coordinates and subtracts half a texel, because GCN forces nearest filtering on integer formats. 2D and 2D array only. WebGPU CTS `textureGather:sampled_2d_coords`: 756 failures to none. (a08)
- `gather` on integer cube and cube array textures. On cubes no shifted direction fixes a08's footprint: near a face edge it takes texels from the neighbouring face, and integer `fetch4` doesn't cross edges. The adapter turns these gathers into four nearest samples at level 0, at the centres of the footprint's texels, found in face space with Metal's face selection (a centre past an edge moves onto the neighbouring face's edge row). WebGPU CTS `textureGather` `sampled_3d_coords` and `sampled_array_3d_coords`: 252 integer cases to none; results match the M3 and the Iris Pro at faces of 8, 64 and 512 texels, edges included. (a17)
- Bitcasts of a vector to narrower lanes (`<2 x i16>` to `<4 x i8>`, from `as_type<uchar4>(ushort2)`, or from the front end itself when only the low bytes of `ushort2` lanes are used): libAMDIL902 leaves the other byte of lane 1 in byte lanes 2 and 3, so the bytes read back wrong once stored. The adapter builds such bitcasts lane by lane. That was all 29 of the AMD failures in the 11,5 session's narrow-vector fuzzing. (a18)
- Float atomics on device memory (MSL 3.0 `atomic_float`: `fetch_add`, `fetch_sub`, `exchange`, `compare_exchange`) crash libAMDIL902, although the GPU reports Mac2. Exchange and compare-exchange run on the integer bits; add and sub use a compare-exchange loop whose retries take the value the failed exchange read (from L2) rather than a possibly stale cached load. 4096 threads on the same addresses give exact sums and unique exchanges, as on the M3. (a19)
- 64-bit integer comparisons that feed a select or a branch make libAMDIL902 stop with "Cannot select"; they're done on the 32-bit halves. (a20)
- Branches on one bit of a 64-bit value (`if ((x >> k) & 1)` on a `ulong`, or the bit-0 split of a `switch` on `uint(x >> k) & 3`): libAMDIL902's DAG combiner turns them into a compare of the 64-bit `and` with 0 whose result is i64, and no pattern takes it ("Cannot select: brcond (i64 setcc ...)"). A bool of high-half bits of a 64-bit product that is sign-extended or selected on meets the same i64 compare in a select. The adapter tests such bits through `extract_bits`, which the combiner doesn't look into. A bool worked out from a 64-bit value in an earlier block meets it too: `bool(a & b)` of 64-bit-derived halves, sign-extended after a loop, came back there as an i64 compare (the 64-bit value arrives with its top half known zero), so such conditions go through `extract_bits` in their users' blocks as well. (a21)
- Signed division or remainder of 32 bits cut from a 64-bit value, `(int)uint(x >> k) / c`, comes out as the unsigned division: libAMDIL902 seems to take the known-zero top bits of the 64-bit value for bit 31 of the cut. The same for any 64-bit value with known-zero top bits, as `(int)uint(x % y) / c`. The adapter builds such dividends from the 32-bit halves, or passes the low half through two 16-bit `extract_bits`. (a22) Also when the cut reaches the division through a loop variable (`uint v = uint(x >> 10); for (i < 3) s += int(v) % 257;`): the AIR keeps the loop, and libAMDIL902 unrolls it afterwards, so the first division saw the cut. (a27) The cut can also pass an unsigned division, remainder or right shift on its way: `(int)(uint(max(x, y) >> 14) / d) / 225` was unsigned for negative quotients (seed 4769); cuts up to two such steps back are built from the halves too. (a22 form 9) A cut of a 64-bit product, `(int)uint(((ulong(a) << 32) * y) >> 24) / 51`, goes through the extracts instead: built from the product's halves, libAMDIL902 took its high half wrong (seed 763, a regression of this fix). (a22 form 10)
- `z + uint(bool(x & min(1u, 145u)))` comes out as `z - bool`: `air.min` / `max` / `clamp` with constant arguments stay calls through libAMDIL902's IR optimizer and fold only in its DAG, where the and with the now-constant 1 is taken for a 0 / -1 boolean. `y % (min(x, 1u) | 1u)` crashed its bit-field-extract combine. The adapter folds such calls to constants, and unsigned `min(x, 1)`, `min(x, 0)`, `max(x, 0)` to `x != 0`, 0 and `x`. (a23) When the constants appear only after unrolling, as `for (i < 3) a += uint(bool(x & min(i, 145u)))`, 32-bit calls whose arguments are constants or loop values become a compare and a select, which the IR optimizer folds after unrolling. (a28) `min(b, y) | 1` with b a bool crashed the same bit-field-extract combine as `min(x, 1u) | 1u` (seed 4629; the front end writes `(min | 1) & 0x7fffffff` as `(min & 0x7ffffffe) | 1`): a min with a 0 / 1 argument, or the constant 1, has its `| odd` folded to the odd constant and its `& even` to 0 (a23 forms 7 and 8); the 0 / 1 argument may also be such a value divided, shifted right or taken modulo something, as `uint(int(bool(..)) / int(d))` (seed 3734, a23 form 9).

The adapter builds `ulong(y) << k` (0 < k < 32) from the halves. (a24)
- A loop exit on the low bits of a square: the front end makes `((x * x) << s) & 3 == 0` into `((x & 1) & (3 >> s)) == 0`, libAMDIL902 takes `x & 1` for a 0 / 1 boolean, drops the `& 1` and tests the whole register, so for x = 2 mod 4 the loop ran on. The bit-test fix (a15) sends that `x & 1` through `extract_bits` too. (a25)

The adapter folds a clamp with equal bounds to the bound; lo > hi is undefined in MSL and left alone. (a30)
- An inner loop's exit on bits of a value and'ed with (or shifted by) the outer loop's counter, `for (i < 3) { while (...) { v ^= ...; if ((i & v & 3) == 0) break; } }`: once libAMDIL902 unrolls the outer loop the test is `(v & 1) == 0`, a15's bug, which the bit-test fix only saw with a constant mask; the inner loop never stopped for i = 1. Such ands (`== 0` / `!= 0`, with a loop counter anywhere in their arithmetic, through selects and the phis the front end makes of them) go through `extract_bits` too. In the same vein, a23's `min(x, 1u)` → `x != 0` made 0 / 1 values that a15's bug misread in a loop exit (a kernel the stock compiler gets right); `min(x, 1u)` now stays a call and only `min(x, 1u) | odd` is folded. (a31, a23 form 6)
- The high half of a 64-bit product whose operand has an unsigned average in its low half, `mulhi((ulong(a + b) << 32) | rhadd(a, b), (ulong(popcount(86u)) << 32) | k)`: it came out 2 too low for most inputs when the other factor folds to a constant late (a literal 4 hides it); libAMDIL902 seems to drop carries out of the average, as with a24's top bits of hadd / rhadd. The adapter builds unsigned 32-bit hadd / rhadd that are widened to 64 bits from bitwise arithmetic, which can't overflow. (a32)
- An inner loop that some lanes of a wave leave early (a `break`, or a data-dependent exit) inside an outer loop that libAMDIL902 unrolls fully: the lanes that had left still took the values of the inner loop's later passes, so `for (i < 4) { while (n < 8) { ...; if ((int(i) / d & 3) == 0) break; } }` came out wrong in every lane of a wave with one lane that loops on. The adapter puts `llvm.loop.unroll.disable` on outer loops with a fixed trip count that hold such a loop whose exit depends on the outer loop's counter. Taken more widely (any outer loop around a loop with a break or a loaded bound), it kept loops rolled in half of Apple's MPS kernels, and Geekbench 7's Background Blur, Face Tracking and Super Resolution failed their validation. (a33)
- The high half of a 64 x 64 bit unsigned product, `mulhi(ulong, ulong)`: with one factor's high half a large power of two (2^31, 2^30) and the other's from a right shift (`ulong(x >> 16) << 32 | y`), the high 32 bits came out as if that high half were 0, in every thread (stock files too). libAMDIL902's 64-bit multiply is at fault, so the adapter builds every scalar unsigned 64-bit `mul_hi` from 32-bit `mul` and `mul_hi` of the halves, with the middle terms' carries. a32's average was most likely the same bug. (a34)
- Constant rotates by a multiple of 8: SC folds the IL's bitalign the other way once it knows both operands (`rotate(37u, 24u)` gave 0x2500), so the adapter writes rotates as shifts. Only rotates that can meet that bug are rewritten now: made shifts, `rotate(~0u, 1u << 31)` folded to a constant that turned `uint(x % (ulong(rotate(~0u, ..)) << 32 | 1))` into an i64 compare in libAMDIL902's optimizer, which no select pattern takes (seed 5463; stock files compile it). Rotates of 0 or all ones, and by constants that aren't a nonzero multiple of 8, stay calls. (a14)
- A test of the low bit after an `if` that may change the value, `r = (a & 1) ? 0 : b; if (r < d) a ^= ...; s = (((a & 1) ? d : 1) & 1) ? ... : ...`: the front end tests a phi of the two `a & 1` values. Once the bit-test fix had made the first test an `extract_bits`, the phi was the `and`'s only user and libAMDIL902 dropped its `& 1`, so 72 of 256 threads took the wrong arm (a regression of that fix: stock files compile it right). The fix now sends the phi's `and`s through `extract_bits` too. (a15 kernel bitphi)
- A single-bit test on 16 bits in a loop exit: `s = select(short2(1, 1), short2(..) & short2(-12131, -9348), ..)` has bit 1 known zero, so the front end makes `(uint(s.x) ^ uint(s.y) * 257) & 3 == 0` into `(s.x ^ s.y) & 1` on `i16`, which a15's bug misreads: the exit tested the whole 16 bits, and 72 of 256 threads ran all 8 passes (stock files too). The bit-test fix only took 32-bit `and`s; 8- and 16-bit ones now go through `extract_bits` of the zero-extended value. (a15 kernel bitshort)
- `(min(150u, K) > b) != bool(min(1u, 104u) & (c / 1522195843u))`: the min/max fix (a23) folds `min(1u, 104u)` to 1 where the call was, so the `and` reads `1 & y` with the constant first, which the bit-test fix didn't recognise; libAMDIL902 then dropped the `& 1`, and y = 2 took the wrong branch in 81 of 256 threads. The bit-test fix now finds the mask in either operand. (a15 kernel maskfirst)
- A `switch` on low bits in an unrolled loop: `for (i < 3) { s = short2(short(i), short(v)) & short2(5474, 29237); switch ((uint(s.x) ^ uint(s.y) * 257) & 3) .. }`. Unrolled, only bit 0 of the switch value varies for i = 0 and 1, and the lowering's bit test misread it (a15's bug): 118 of 256 threads took the wrong case (stock files too). Switch values that are `x & (2^w - 1)` (or the zext of an 8- or 16-bit one) now go through `extract_bits(x, 0, w)`. (a15 kernel switchbit)
- A single bit compared with a bool in an unrolled loop: `for (i < 3) if (((c & 1) % (i | 1)) == uint(!((a ^ (t << i)) > b))) r = ...`. The front end compares the remainder with the zero-extended bool, and libAMDIL902 dropped the `& 1` as in a15, and 62 of 256 threads took the wrong branch (stock files too; the same compare without the `%` or without the `!` is right). In `x == b` / `x != b` with b a zero-extended bool, the `y & 1` in x, directly or under an unsigned division, remainder or right shift, now goes through `extract_bits(y, 0, 1)`. (a15 kernel bitbool)
- The narrow (8- and 16-bit) integer operations libAMDIL902 gets wrong are done in 32 bits, but unsigned operations on provably exact values (small constants, arguments, loads, non-wrapping arithmetic and bitwise operations of exact values) stay native, so loop counters keep a trip count the compiler can see. Without that, Apple's MPS kernels (`ushort` loop counters and thread positions) failed Geekbench 7's validation and its Super Resolution took 25 minutes instead of 47 s. Geekbench 7 Metal now validates every workload on the R9 M370X. A narrow vector loaded from a buffer and also used as an integer (`char4(..) != as_type<char4>(in[i])` beside `ushort(in[i])`, which the front end loads once as a char4) is widened lane by lane from its bits: its zero extension became an extending <4 x i32> load that libAMDIL902's combiner left the integer use on, "Cannot select: i32 = bitcast" (seed 675; stock files compile it). A loaded 3-lane vector in a signed comparison is extended lane by lane too: extended whole, libAMDIL902 folded the extension into the load as a <3 x i32> one and read lane 2 at byte 8, past a `short3`, from the struct's padding. MPS's image kernels bound-check their thread position against a `short3` size in parameters whose padding MPS leaves uncleared, so `MPSImageAdd` and `MPSImageMultiply` wrote nothing whenever a leftover pointer there read as a negative depth, about half the calls; a sweep of 35 MPS image filters and CNN kernels now matches the M3 on the R9 M370X (only 8-bit rounding of the last bit differs, as on the Iris Pro). `AMD_NARROW_LOAD3_FIX=0` leaves the whole-vector extension. (a16, kernel loadedvec; r02 guards it)
- A cube array index below 0. GCN clamps the slice, `8 * index + face`, so -1 reads the first face of the first cube whatever the direction. WebKit and Firefox pass WGSL's index on as it is, and WebGPU asks for the nearest layer. The adapter raises the index to 0 first. WebGPU CTS `shader,execution`: 2414 Safari failures and 2053 Firefox failures gone. Safari fails the same cases on an M3 Pro, so this goes further than matching Apple silicon. (a09)
- `threadgroup bool`. LLVM shrinks a threadgroup variable that only ever holds two values to an `i1` global, and libAMDIL902 miscompiles `zext` of its load: `iand load, r`, with `r` holding an unrelated 0, so it always reads as false. The adapter loads the byte and compares it with 0. WebGPU CTS `workgroupUniformLoad:types`, `type="bool"`, in Safari. (a10)
- Multisample texture reads on the `12.5-24` driver (Sequoia without MetalOld), from riptidewave93. A `texture2d_ms` read first loads the texture's FMASK descriptor from a table (API slot 13) that this driver copy never sets for render stages, so a fragment shader loads from GPU address 0 and the GPU resets; compute reads get wrong samples. Safari reset the GPU on every antialiased WebGL canvas. Both encoders expand compressed MSAA textures when they're bound, so the adapter replaces each FMASK lookup with the identity map, and the descriptor load goes away. Only on Sequoia (Darwin 24) where OCLP's `impostor.dylib` is installed: Tahoe's `12.5-25` and `12.5-GCN-SKL-25` link it too, but set the FMASK table, and there the identity map reads the wrong samples (a11 and s25 failed, wrong colours in Chrome and VS Code). `AMD_FMASK_FIX=0/1` forces it off or on. (a11)

## 4. `IntelTextureAtomics.dylib`

Weak-loaded by libMTLIntelCompilerPlugin (`12.5` for Haswell; `11.7.10` and `11.7.10-22` for Ivy Bridge), Intel shader compiles only. Source: `IntelAdapter/`.
- Texture atomics on the Intel back end. (a01 on Intel; on Ivy Bridge through its plugin's own entry points, below)
- Array-of-struct buffer arguments crash the Intel compiler (Firefox WebGPU). (i01)
- Textures through stored pointers crash the Intel compiler, the same WebGL shader as above. (a05 on Intel)
- Two metadata attributes from the newer front end that the back end aborts on.
- Signed bytes and halfwords in vertex functions. The sign-extended top lane of a word read from a constant buffer (`char4(x).w`, `unpack_snorm4x8_to_float(x).w`, ...) came from the first word of its 16 bytes when it wasn't that word. ANGLE's vertex shaders unpack their Y flip that way, so on these GPUs every WebGL draw collapsed. Done with shifts of the word now. (i02)
- Depth comparisons with an LOD bias (`texture(sampler2DShadow, coord, bias)`) abort the compiler service, and in Chrome the GPU process with it; the compiler can't compute an LOD either. The bias is dropped. (i03)
- Integer textures ignore the texel offset of a sample or gather (`textureOffset`, `textureGradOffset` and the like on `isampler2D`, `usampler2D`, ...). The offset goes into the coordinates instead, in texels of the level the sample reads. Where the GPU would pick that level (gradients, or an implicit LOD in a fragment function), the shader computes it and samples there explicitly, so the offset and the texels come from the same level. dEQP `textureoffset`, `textureprojoffset`, `texturegradoffset` and `textureprojgradoffset` now pass in Chrome, apart from the two shadow cases below. (i04, a08 on Intel)
- In compute kernels the back end adds a gather's texel offset to the normalized coordinate as is (`FADD coord, 1.0` for an offset of 1), so each texel of offset moved the gather a whole texture width, on every format (WebGPU CTS `textureGather` `sampled_2d_coords` and `sampled_array_2d_coords` with offsets in compute: 621 cases each). Vertex and fragment functions are right. Those gathers get the integer-texture rewrite above: the offset goes into the coordinates in texels of level 0. Both queries now fail only `rg32float` (108 each, a separate problem). (i19) Depth and compare gathers get both rewrites too (this one and the cube sampler above): `textureGather` `depth_*_coords` pass in full.
- Gathers of the green component of R32G32 textures (`rg32float`, `rg32uint`, `rg32sint`) return red: a gather4 erratum of Haswell and Ivy Bridge. Mesa works around it with a separate surface state for gathers (format R32G32_FLOAT_LD, green read as blue), which this driver doesn't have, and the shader can't tell an R32G32 texture from any other. The adapter does a green gather from a 2D texture or 2D array also as a red one, and where the two agree in all four texels (the erratum, or a texture whose red equals its green there) takes the green values from four level-0 samples at the footprint's texel centers instead, through the same sampler, so its address modes apply (at a texel center a linear filter returns that texel). WebGPU CTS `textureGather`: 216 of the 252 `rg32float` cases now pass; cube gathers, whose footprint can cross face edges, keep the erratum (the other 36). The comparison of the two gathers is done on integers of the lanes' width: as <4 x i32> it was invalid for a `half4` gather and the compiler service aborted, so MetalFX's spatial scaler (`MFX_Scale`, `half4` gathers) failed to build and `MTLFXSpatialScaler` came back nil on the Iris Pro while `supportsDevice` said yes; it now upscales like the M3. The HD 4000 has the same erratum and gets the same fix. (i50, i72)
- Integer builtins, found by the MacBookPro11,5 session's second fuzzer (195 of 300 random kernels wrong on the Iris Pro): `madsat` is lowered without the carry out of its addition (`madsat(a, 3u, b)` returned the wrapped `a * 3 + b`), `mulhi` with a constant operand returns 0, and `addsat` of two constants is folded as a plain add (`addsat(95u, 4294967295u)` = 94). `madsat`, `mulhi` and `madhi` are done with 32-bit operations (the high word from 16-bit partial products), and constant `addsat` / `subsat` are folded exactly. (i21)
- `min`, `max` and `clamp` on 8- and 16-bit integers against a constant of 128 or more: the back end compares the zero-extended variable with the sign-extended constant (130 becomes -126), so `min(uchar2 a, uchar2(130, 183))` returned `a` and `clamp((uchar)y, 100, 200)` returned `y` (the 11,5 session's narrow-vector fuzzing). They're done on 32-bit lanes (i22). The back end also sign-extends the constant lanes when it extends a vector that mixes them with a variable lane, as `uchar4(x, 156, 0, 0)`, so `min` still kept 157 against 156 there: such vectors are extended in the IR, the constant lanes folded and the variable ones extended one by one, for i31's narrow division too. (i35) So is a vector ORed (or ANDed, XORed) with constant lanes: `uchar2(0, b) | uchar2(199, 32)` in a `max` reached the back end as an `OR` with `MOV r, -57`, and the max always picked 199 over bytes 200-255 (`mslfuzz2` VEC seed 2464; the stock compiler too); the extension goes through the bitwise operation, its constant operand zero-extended. (i51)
- Integer functions of constants (`max(0, 0x04030201)`, `clamp` of constants, `popcount(0xF0u)`), which the front end leaves as calls: iCBE folds them itself and then reads every byte of the folded value as byte 0 in a multiply, so the `uchar4` lanes of `as_type<uchar4>(max(0, 0x04030201))` times 7 all came out 7. The IGIL is right. The adapter folds such calls, and every instruction that then has only constant operands, so the back end gets the finished constants. (i36) `reverse_bits`, `rotate`, `extract_bits` and `insert_bits` of constants are folded too: `(uchar)reverse_bits(60u)`, which is 0, fed a signed divide whose result picked the bits of a later `extract_bits`, and 54 of 256 threads came out wrong (`mslfuzz2` plain seed 849); with the literal `0x3C000000u`, or `reverse_bits` of a variable, it was right. (i39) A vector `as_type` of such a folded call (`as_type<short2>(min(194u, 253u)) & short2(15)`) is a bitcast that the 3802 LLVM keeps as a constant expression, and reading it lane by lane crashed the compiler (`mslfuzz2` VEC seed 734): those bitcasts are folded to their lanes, and constant vectors that aren't plain data are left to the back end. `clz` and `ctz` of constants weren't folded at all, because AIR calls them with a second, `i1` operand: iCBE folded them and unpacked `as_type<ushort2>(clz(1827419243u))` as (1, 1) instead of (1, 0), so a vector lane picked with it was the wrong one in every thread (VEC seed 896). (i42) Calls that only become constant once another call is folded are folded too, until nothing changes, and `hadd` / `rhadd` and the saturating add / subtract of scalar constants with them: `extract_bits(65599u, 0u, addsat(~1u, hadd(65536u, 36u)) & 15u)` is 63, but once `hadd`'s value was known the back end folded the `addsat` as a plain add, so the bit count came out 0 (`mslfuzz2` VEC seed 4630; the stock compiler too). (i56) `min3`, `max3` and `median3` of constants too: `as_type<uchar4>(as_type<ushort2>(min3(240u, 239u, 177u)))` got every byte as byte 0 (`mslfuzz2` VEC seed 5854; the stock compiler too). (i58) And `extract_bits` / `insert_bits` with a constant bit count of 0, whatever the other operands: MSL gives 0 and the base, but the back end lowers them with a shift by the width, which LLVM folds as poison, so `w[(uint)((long)(1u | extract_bits(v0, 0u, 0u)) >> s) & 3u] = 1u` stored to `w[1]` in every thread (`mslfuzz2` LONG seed 2575; the stock compiler too). On Ivy Bridge that took one more step: once folded, the index is a 64-bit shift of a constant, which its compiler again made a constant lane 1, so the lane selects below now also run after the fold. (i59)
- The negation of a `char` vector lane: the back end writes `0 - x` as a byte add of the negated operand followed by the sign extension, and iCBE folds the two into the negation of the sign-extended lane, so for 0x80 the lane read back as +128 instead of -128 (scalar chars, shorts and zero extensions are right). Such negations are written as an XOR with 0xFF and a byte add of 1. In the 11,5 session's narrow-vector fuzzing, that was both kernels still wrong among seeds 1-220. (i37)
- A saturating add of 0 and a byte: the back end writes `addsat(0u, x & 255)` as `UADD_sat r, 0, (x AND 255)`, and iCBE turns that into something that reads another byte, so `v + addsat(0u, (uint)c)` with a `uchar c` got the wrong byte in 110 of 256 threads (also the signed form, and other uses of the same masked value). An `add_sat` with a zero operand, or a `sub_sat` of zero, is its other operand and is folded away in the IR, with the saturating adds of two constants (i21). The 11,5 session's `mslfuzz2`, plain seed 812. (i38)
- `c ? in[i] : in[j]`, which the front end turns into a load through a select of two pointers into one buffer: the back end can't tell they name the same buffer, so it loads through a loop over the SIMD group's distinct surfaces, and that loop takes flag register f0.1 without saving it. In the then-branch of an if/else whose else-branch keeps its condition in f0.1, the lanes that took the else came out as if the condition held: a `switch` whose case 0 just breaks ran the default's code in every SIMD8 group with a case-1 lane (3 of the 7 kernels still wrong in the 11,5 session's `mslfuzz2` run; I read the loop in the kernel's disassembly). A select whose arms address the same buffer becomes one address with the index selected. (i23)
- `sample_compare` with an explicit level in compute kernels: the IGIL writer builds the message in one register (coordinates and LOD) and then names the coordinate register as the operand, and the back end takes the LOD from its w, which nothing wrote when the coordinates came from a select of 2-component values (Dawn loads them from its argument array). The sample came from a random mip level, and with a linear mip filter a random blend, so the results changed from run to run (WebGPU CTS `textureSampleCompareLevel` in compute: 160 cases). The operand is corrected in the IGIL text, for 2D samples (a cube array's operand carries its array index there). Haswell only. (i24)
- Signed division of a negated value: the Intel compiler folds the negation (`0 - v`) into the integer divide as a source modifier, and the divide drops it, so `(-v) % d` came out as `v % d`, and `(-v) / d` and `v / (-d)` as `v / d` (unsigned division is right). Such divides are done on `v` and the result negated (`INT_MIN` kept). In the 11,5 session's `mslfuzz2` that was 4 of the 300 kernels; none is wrong now. The IR doesn't always show the negation: `(short)(-(int)v) % d` arrives as `(v * -65536) >> 16`, which the back end turns into `IADD r, 0, -v` when it knows `v` is 0 or 1, and the remainder was `v % d` in every thread (`mslfuzz2` VEC seed 917). An `IDIV` operand set by such an `IADD` is computed as `XOR -1` and `IADD 1` in the IGIL text instead (Haswell only). (i26) A negation that reaches the divide through copies is rewritten too, merges included: `v2 = -(int)x` in one case of a switch, falling through into a loop that the back end made a subroutine, gave `(int)v2 % 65535` 0 instead of -1 (`mslfuzz2` LONG seed 2592; the stock compiler too). (i60) And one that reaches it through operations iCBE folds into copies: `v0 = -(int)(x & 0x7fffffff); v0 -= min(mulhi(..., 0u), 0u)` arrived as `IADD r80, r78, -r79` with `r79` a `UMIN` of two zeros, and `(int)v0 / d` came out as `(x & 0x7fffffff) / d` (`mslfuzz2` plain seed 7727; the stock compiler too). Every such negation in a shader with an `IDIV` is now done as `XOR -1` and `IADD 1`, whatever leads it to the divide. (i61)
- 64-bit multiplies: the back end splits them into 32-bit ones and hits the constant-operand high-word bug of i21 whenever a factor's low word is a known constant (`(x << 32) | 139`): the high word of `a * b` and `mulhi(a, b)` came out wrong. 64-bit multiplies other than a 32-bit value widened by another (every buffer index), and 64-bit `mulhi` / `madhi`, are built from 32-bit limbs with the exact high word. (i27)
- Signed division by a constant power of two: the Intel compiler turns `x / 2^k` (and `/ -2^k`) into an arithmetic shift, which rounds toward minus infinity, so `-7 / 4` gave -2 instead of -1 for every negative dividend that isn't a multiple: plain `int / 2` on negative values. Such divides get the rounding correction. (i28)
- Narrow integers in the Intel compiler's last stage, all found with the 11,5 session's narrow-vector fuzzing and read off the IGIL text or the disassembly: it took an `AND 0xFFFF` that re-truncates a 16-bit lane right after an `AND 255` for a zero-extension of the first one's source and dropped the 255, so a `uchar` lane widened into a `ushort2` kept bits 8-15 (i29); it drops the mask that truncates the operands of its narrow unsigned divides (`UBDIV`, `USDIV`), which read the whole register, and narrow constants arrive sign-extended (i30). The first becomes a `MOV`, the second a 32-bit divide of masked copies, in the IGIL text (Haswell only); 8- and 16-bit division and remainder are also done in 32-bit lanes in the IR (i31). The dropped 255 also happens through copies, as into the register a `switch`'s shared case takes, where the 16-bit AND has to stay for the other path: it becomes `(x | bit 31) & (mask | bit 31)` with bit 31 XORed away (i32). It used to be a shift pair, but where the source was itself a narrow AND (`AND 0xFF` over `x & 3`) iCBE kept it in a byte register and `SHL 24` lost it, so a loop's exit test compared against 0 (`mslfuzz2` VEC seed 1111; i43).
- A vector lane picked by a 64-bit quotient (`w[q & 3]`): the back end expands 64-bit division into loops, and the lane's index was read from a register the loop hadn't written yet, so with a constant dividend the lane picked was the dividend's low word, whatever the quotient (the quotient itself was right). Such lanes are picked with selects. A lane picked by a 64-bit shift of a constant, `w[(uint)(4151055293ul >> s) & 3]`, crashes the stock back end in its DAG legalizer (`mslfuzz2` LONG seed 378); those get the same selects, also when the integer-function fold above makes the shift's base constant (i59). (i33)
- A right shift of a narrow value merged with a wider copy of the same variable: the Intel compiler gives `SHR` / `SAR` of a constant below 65536, or of a value masked with `& 255` / `& 65535` (a `uchar` or `ushort` cast), a result register only as wide as that value, and can then merge it with the variable's other copies. `v0 = (uint)(x / y)`, replaced in a loop by `(uchar)1 >> s`, came out as the quotient's low byte in every thread, also where the loop never replaced it (`mslfuzz2` LONG seed 6; the 64-bit division only set up the merge), and a vector lane lost its upper bits the same way (VEC seed 526). An `AND` with such a mask is narrow too: `(ushort)(x >> s)` in one arm of a select and a 64-bit quotient in the other kept only the quotient's low 16 bits (LONG seed 314). The IGIL is right; constants from 65536 up, `SHL`, and `AND` / `UMIN` with a constant in a register were fine. Such shifts are done on the value with bit 31 set and the shifted bit 31 XORed away, and such an `AND` whose result is copied into a merged register (one that two or more `MOV`s set, as the back end writes phi values) becomes `(x | bit 31) & (mask | bit 31)` with bit 31 XORed away, in the IGIL text. Haswell only. (i40) So is such an `AND` that a min / max or a signed operation reads: with i22's widening, `max(short3(...), short3(~c, d & 255, ...))` reached the back end as `IMAX r, 0, (d AND 255)`, which took `d & 255` as a signed byte and gave 0 for 200 (`mslfuzz2` VEC seed 1889; the stock compiler is right). - Comparisons at an explicit level on 2D-array and cube depth textures in compute kernels: at any level but 0 they compared against the wrong data, on the HD 4000 with the stock compiler too (a native `ta.sample_compare(s, uv, 1, ref, level(1))` failed for both references, while plain samples and reads of the same level were right). It's the same IGIL message as the 2D case above (explicit-LOD sample coordinates): the coordinates and LOD are built in a new register, but the old coordinate register, whose `w` nothing wrote, is named as the operand. That fix now covers 2D-array and cube comparisons too; cube arrays keep the array index in `w` and are left alone (a09). Found while checking that gradient comparisons select their level (i78; `INTEL_SAMPLE_LOD_OPERAND_FIX=0`).
- Comparisons at an explicit level on cube arrays took their level from the array index: layer n compared at level n whatever level was asked for, on Ivy Bridge and Haswell, with the stock compiler too, in compute kernels and fragment shaders (found by the MacBookPro11,5 session). The IGIL message (`SAMPLE_LC ..., CUBEARRAY`) has the array index in the coordinates' `w`, and iCBE reads the LOD from that `w` as well, so the fix above can't help. iCBE's projective form, `SAMPLE_PLC`, takes the LOD as an operand and the index from `w`, but divides the coordinates and the reference by `w`. So they're multiplied first by w' = max(index, 2^-8), which the division undoes and the sampler still rounds to the same layer; with a linear mip filter the levels blend as on a cube (i79; `INTEL_CUBE_ARRAY_LEVEL_FIX=0`).
- Loops that never exit: a block whose only instruction branches back to itself, which LLVM leaves where a loop can't advance for the function constants a kernel was specialized with. MPS's `reduce_multiple_passes_axes_*` kernels keep several, entered when a stride is 0; nested in the ones MPSGraph specializes for a reduction or softmax along an outer axis (`reductionMaximum` / `softMax` over axis 0 of a 2D tensor), the back end never finishes compiling them (`USC::CompileComputeShaderOpenCL_Gen7` spins at 100%), with the stock compiler too, so the app waited forever (on Tahoe; Sequoia's MPSGraph builds these kernels differently and doesn't hit it). A thread that reached such a loop would hang the GPU, so it returns instead. With this and MetalOldCompat item 43, an MPSGraph sweep of 31 operations (matmul variants, convolutions, pooling, reductions, softmax, normalization, gather, resize, elementwise) matches the M3 on the Iris Pro. `INTEL_INFINITE_LOOP_FIX=0` turns it off. (i71)

## 5. `AMDBronzeCompat.dylib`

Weak-loaded by AMDMTLBronzeDriver (`12.5`, `12.5-24`, `12.5-25`, `12.5-GCN-SKL-*`), so in every process using the driver, including on AMD-only Macs and Tahoe, where the Metal wrapper and item 1 don't load. Source: `BronzeCompat/BronzeCompat.m`. Based on riptidewave93's bronzefix.
- Stencil through texture views of mip 1+. The driver's view init counts the view's first level twice in the stencil-plane index, so the write lands on level 0 / slice 0. (s17)
- sRGB mipmaps: the driver's blit averages the encoded bytes, so levels below 0 come out too dark. (s12)
- Blends linearly between mip levels. The 12.5 driver sets `PERF_MIP` in every sampler, so trilinear filtering reads a single level near whole levels and blends only in between (level 0.25 returns 0.19 of the way to the next level). Apple's GPUs blend linearly, and EEVEE samples its depth pyramid just above whole levels: light from bright emitters went missing on nearby surfaces. It costs up to ~12% in a kernel that does nothing but sample textures; Blender's render times didn't change. `AMD_EXACT_TRILINEAR=0` turns it off. (s19)

- sRGB MSAA resolve: the driver averages the encoded bytes, so antialiased edges come out too dark. These attachments now get resolved in a shader. On `12.5-24` that shader read needs item 2's FMASK fix (riptidewave93), without which it resets the GPU. (s25)
- Depth or stencil copied to a buffer with row pitch 0, which wgpu passes for a single row: the driver writes nothing for one aspect of a combined depth/stencil texture. (s26)
- WebKit's one-vertex pipelines. For a draw of one vertex, WebKit copies the pipeline with the stride set to the end of the last attribute, 2 for `snorm8x2`. The driver refuses a stride that isn't a multiple of 4, WebKit then draws with no pipeline set, and the driver crashes, taking Safari's GPU process with it. In WebKit's processes the stride goes up to the next multiple of 4. (s29)
- WebKit's sample mask of 0. The driver takes it to mean no mask and draws every sample, where nothing should be drawn. In WebKit's processes it becomes a bit past the last sample of any target. WebGPU CTS `occlusionQuery` `sample_mask`: 16 failures to none. (s30)
- Memoryless textures, from riptidewave93. Only Apple GPUs have that storage, and Metal's descriptor validation aborts on it from the driver's texture init. Item 1 prevents that only where it loads, so GCN-only Macs on Tahoe still aborted. The driver now gets a copy of the descriptor with private storage, and `AMD_BRONZE_MEMORYLESS=0` turns that off. Heap, buffer and IOSurface textures with memoryless still abort, as on any non-Apple GPU. (s27)
- MSL 3.2 device coherence on buffers, from riptidewave93. With native Metal (GCN-only Macs), MSL 3.2 compiles, but the driver's compiler fails any buffer with device coherence when the pipeline is made. SPIRV-Cross emits `coherent device T *` for every Vulkan `Coherent` storage buffer, so MoltenVK couldn't create those pipelines (`VK_ERROR_INITIALIZATION_FAILED`). In MSL 3.2+ source compiled on this driver, `coherent(device)` and `coherent device` become `volatile`, as item 1 does on MetalOld (coherence is Apple silicon only). Coherent textures and threadgroup coherence compile and are left alone. (s09)
- Viewports 1-15 before the app sets a viewport: the driver sets up only viewport 0, so the others cover nothing (on Apple GPUs all 16 start at the render target). wgpu's multiview maps view i to viewport i and sets a viewport only when the app does, so `multiview::draw_multiview` and `draw_multiview_multisample` left layer 1 at the clear color; primitives a vertex function sends to viewport 1+ with `[[viewport_array_index]]` were dropped too. Each render encoder now starts with the default viewport set, which the driver's `setViewport:` copies to all 16: `renderTargetWidth`/`Height` when given, otherwise the smallest attachment, which is what the driver uses for viewport 0. `AMD_BRONZE_VIEWPORTS=0` turns it off. (s56)
- Depth of mipmapped depth-stencil textures read by shaders. The driver pads the depth plane's pitch at small levels to what the stencil plane needs, which the texture unit doesn't know about, so shaders read the depth of levels 4 or fewer texels wide from the wrong place: in WebGL, `depth24_stencil8` shadow lookups and texture storage checks (dEQP `textureshadow`, `texstorage*_format_depth_stencil`). Such textures made with shader-read usage get their depth plane without the padding, as radeonsi does. `AMD_BRONZE_DEPTH_MIPS=0` turns it off. (s44)
- Stencil8 textures with several levels or slices. The driver gives them a tiling only one level and slice survive, so blits, render passes and shaders address the rest three different ways (WebGPU `stencil8` textures with mips or array layers in Safari and Firefox). They're made as Depth32Float_Stencil8, which is right everywhere, and report that format; Stencil8 views of them are X32_Stencil8 views. `AMD_BRONZE_STENCIL8=0` turns it off. (s37, s48)
- Depth-stencil textures attached as stencil only. With no depth attachment the depth unit keeps a leftover depth tiling and misaddresses the stencil of these formats on textures up to 32 texels wide: a stencil test passed for a quarter to a half of the texels, some in the wrong place, and REPLACE wrote half. ANGLE attaches a packed depth-stencil buffer this way when GL binds it as `GL_STENCIL_ATTACHMENT` only. Such passes get the same texture attached as depth too, loaded and stored, and each depth/stencil state is swapped for a copy that neither tests nor writes depth, as on an M3, where a pass without a depth attachment does neither (a compare of Never still rejects everything, as there). `AMD_BRONZE_STENCIL_DEPTH=0` turns it off, `AMD_BRONZE_STENCIL_DEPTH_STATE=0` only the state copies. (s47, r03)
- Buffer copies into a texture view of slice 1 or higher. A copy from a buffer into such a view (a single-face 2D view of a cube, a view of a 2D array's slice 1+) that covers the whole slice was written nowhere; smaller regions, views of another level only and texture-to-view copies were right. These copies now go to the parent texture at the view's slice and level, when the view has the parent's pixel format. `AMD_BRONZE_VIEW_UPLOADS=0` turns it off. (s65)
- Reversed viewport depth ranges (znear > zfar, which Metal allows; MoltenVK passes Vulkan's through). The driver maps depth right, but stores the depth clamp range unordered, so the clamp turned every fragment's depth into zfar: viewport depth 1..0 stored 0 for z = 0.25 instead of 0.75, and 0.75..0.25 stored 0.25 instead of 0.625. This one is a patch to AMDMTLBronzeDriver itself, since the driver emits the range in the same call that computes it: build.sh's `tools/fix_bronze_driver.py` makes `amdMtlBronzeSetViewports` store it ordered (38 bytes, as OpenGL's branch of the same function already does), in all seven driver variants. WebGL wasn't affected: ANGLE swaps such ranges itself. (n21)
- Wide points centered outside the viewport. The driver culls points against a discard band it leaves at the viewport itself, so a point whose center was outside the viewport drew nothing, not even its part inside (8-pixel points 0.4 px past the edge drew 0 of 32 pixels; WebGL `clipping-wide-points`). The same `tools/fix_bronze_driver.py` sets the discard band to the clipper's guard band, as radeonsi does, both for the render target's default viewport and in `amdMtlBronzeSetViewports`; the viewport scissor still keeps every pixel inside the viewport. (n23)

## 7. Haswell's framebuffer: Linux's RC6 thresholds

`AppleIntelFramebufferAzul.kext/Contents/Info.plist`, `RCxControl`, in `Universal-Binaries/12.5`, `12.5-23` and `12.5-23.4`. The Monterey framebuffer OCLP installs for Haswell programs the GPU's RC6 (render standby) timers from `RC6_Threshold` 520 and `RC_Eval_Interval` 26000, in 1.28 µs units (registers 0xA0B8 and 0xA0A8), so the render engine enters RC6 far sooner than under Linux (below). On the Iris Pro 5200, Safari's WebGL video uploads (bursts of small submissions from ANGLE, CoreImageOld and video decoding in one GPU process) hung the GPU on its way out of RC6. All 8 Intel GPU Hang Summaries I collected look the same: the render ring is "hung in the ring" at the first command of the next submission, the last instruction it parsed is `3DSTATE_VF` (the end of a render-context restore), the media, blitter and video-enhancement rings wait on the semaphores the render ring signals after every batch, and every ring has sleep messages enabled (`RC_PSMI_CTRL` 0x10). That's the gen7 hang Linux works around in 2c550183 ("drm/i915: Disable PSMI sleep messages on all rings around context switches"), and Linux programs RC6 far less eagerly on Haswell: `GEN6_RC6_THRESHOLD` 50000 in a `GEN6_RC_EVALUATION_INTERVAL` of 125000. Those are the values here. Once, WindowServer didn't survive the GPU restart, and watchdogd panicked the Mac. With RC6 turned off (`RenderStandby` 0) or with these values, the video pages run without a GPU reset (11,4 results); these values keep RC6 for an idle GPU. OCLP copies this `Info.plist` as it is apart from `OSBundleRequired`, so nothing else needs to change.

## 8. `GeForceAIRCompat.dylib` (Kepler)

Weak-loaded by GeForceAIRPlugin (`11.0 Beta 3`), the Kepler (GTX 600/700) back end, Kepler shader compiles only. Source: `NVIDIAAdapter/`. The plugin runs on the shared 3802 libLLVM, so the adapter hooks it like the Intel one: before each `llvm::legacy::PassManager::run`, it rewrites the module. Measured on a GTX 770, each operation against the CPU over 4096 random input pairs (33 operations, all right with the adapter).
- AIR intrinsics newer than the plugin (2020). The plugin gives the ones it knows a body from its built-in library and selects a few `air.simd_` shuffles by name; every other one stays a bare declaration, which instruction selection takes for an external call and fails on ("Unhandled constant"). Among them are every 64-bit `min`, `max`, `mulhi` and `madhi`, so 64-bit integer code (Blender, the fuzzer) made no pipeline. Bodies for `min`, `max`, `clamp`, `popcount`, `clz`, `ctz`, `mulhi` and `madhi` on 64-bit integers and for `quad_shuffle_xor`, inlined. (i49; a21, a22, a34 and i27 on Kepler)
- A bool widened to 64 bits (`ulong(a < b)`, `long(c) * -1`) kept a garbage high word: the low register of the pair is set, the high one isn't. Built as 0 or 1 through the plugin's own 32-bit `min` instead, which its optimizer can't fold back into the widening.
- 64-bit division and remainder, signed and unsigned, were wrong for most inputs, by constants too (those become a 64-bit multiply-high, which is wrong as well). Done by 64 unrolled steps of shift and subtract, as straight-line code: a first version with a branch and a loop let the plugin misorder private-array accesses around two divisions (a store indexed by one division read back by the other: mslfuzz2 LONG=1 seed 770).
- 64-bit shifts by a variable amount are built from 32-bit shifts of the halves: next to straight-line code in a fragment function, `long >> s` came out as an unsigned shift (i67). They combine the halves through masks, with an amount the optimizer can't bound: a first version chose with selects, which the optimizer turned into predicates and a widened bool where it could tell the amount was 0 or 1, and Kepler's code generation got that wrong next to a threadgroup load after a barrier (the result came out 0; LONG fuzz seeds 1295 and 1853), though the IR was right. (n06)
- 64-bit `reverse_bits` and `abs` had no body either ("Unhandled constant"); now they do.
- Differential fuzzing on the GTX 770 (`Tests/fuzz`, `BUILD=1`): seeds 1-1000 in plain, `LONG=1`, `VEC=1 ASTYPE=1`, `FRAG=1` and `GEN=mslfuzz.py`, and 1001-2000 in plain and `LONG=1` so far. The 34 kernels that differed from the CPU across them all match with these fixes.
- Vectors of 64-bit integers (`ulong2 / ulong2`) get both fixes one lane at a time. (i67 on Kepler: 64-bit division in a fragment function)
- With these, tests written for other GPUs' 64-bit bugs pass on Kepler too: a14 (saturating add and subtract, rotate, modulo), a27, a32, i33 and i40.
- Threadgroup bools: LLVM shrinks one to an `i1` global, and on Kepler a value stored to it never arrived (the output kept its fill; WebKit's WebGPU `workgroupUniformLoad` on bool). Widened to a byte, as on Intel. `NVAIR_THREADGROUP_BOOL_FIX=0` turns it off. (a10 on Kepler)
- Cube array indices below 0 read another cube than the nearest: raised to 0 first, as on AMD. `NVAIR_CUBE_ARRAY_FIX=0` turns it off. (a09 on Kepler, with the next fix)
- Gradient samples of 3D textures, cubes and cube arrays (`gradient3d`, `gradientcube`) in compute kernels broke the kernel: its stores after the sample never happened (2D and 2D-array gradients, and every gradient in a fragment function, are right). In compute modules they're done at the level the texture unit would pick (OpenGL's and Vulkan's formula without anisotropy; for cubes on the major axis' face coordinates), from the texture's size. `NVAIR_GRADIENT_FIX=0` turns it off. (i08 and a09 on Kepler)
- The level of cube samples with gradients in vertex and fragment functions, and of 3D ones in vertex functions. Kepler's own level for a cube gradient with a component along the major axis was wrong. For one along it, the level rose by about 0.64 per doubling of the gradient and stopped at level 2; diagonal ones switched levels at 0.67, 1.80 and 3.14 instead of 0.5, 1.5 and 2.5. That is how the difference of the face coordinates of p + d and p behaves, which saturates as d grows, instead of their derivative; gradients within the face were exact (Khronos WebGL 2 deqp `texturegrad.isamplercube_vertex` and `_fragment`). Those samples now take the level the compute-kernel fix above computes, from the derivatives of the face coordinates. In ANGLE's vertex shaders, 3D gradient samples failed deqp's `isampler3d_vertex` cases of `texturegrad`, `texturegradoffset`, `textureprojgrad` and `textureprojgradoffset`. They pass at the explicit level, so 3D gradient samples in vertex functions get it too. Natively the same samples matched the explicit level at every vertex (deqp's 93x93 grid of coordinates and gradients, RGBA8Sint, a runtime sampler, attributes from a buffer), so what differs in ANGLE's shaders isn't found; where the hardware is right the level is the same, and these samples lose anisotropy in vertex functions only. 3D gradients in fragment functions keep the hardware's level. With both, Chrome passes all 15 deqp shader-texture-function pages (11.7 million subtests; 6 failed before). `NVAIR_CUBE_GRADIENT_FIX=0` and `NVAIR_VERTEX_3D_GRADIENT_FIX=0` turn them off. (n27, the cube part)
- Depth comparisons (`sample_compare`) with an explicit level or a bias that isn't a constant 0 returned the texel's depth instead of the comparison (`level(1.0)`, `level(0.4)`, `bias(5.0)`; a one-level texture too; ANGLE's `texture(sampler2DShadow, coord, bias)`). Nothing compares above level 0 on Kepler (gradient comparisons have no body either), so explicit levels compare at level 0, exact for one-level shadow maps, and in fragment functions a bias compares at the implicit level, as on Intel. `NVAIR_COMPARE_LEVEL_FIX=0` turns it off. (i03 on Kepler; s31, where ANGLE's fallback for `textureGrad` on a shadow sampler, a comparison at a computed level, gave the depth)
- Constexpr samplers from metallibs built for macOS 15.4 or later (Xcode 16.3+, `[2 x i64]`) trapped the plugin ("Compiler encountered an internal error"): iMovie 10.4.4's viewer shader among them. Rewritten in the one-word form the plugin reads, as on Intel. `NVAIR_SAMPLER_STATE_FIX=0` turns it off. (i05 on Kepler, through MTLCompilerService, where item 25 retargets the library)
- Private arrays of bytes and halfwords (`uchar pc[8]`) are stored with truncating stores and read with extending loads, and Kepler's back end forwarded a stored 32-bit value to such a load without masking it: where a 64-bit product and compare used `pc[i]`, it kept the bits above its byte (mslfuzz2 `LONG=1` seeds 575 and 770). The same bug as Intel's i47; such arrays are done on 32-bit words. `NVAIR_NARROW_PRIVATE_ARRAY_FIX=0` turns it off. (n02)
- Device-memory loads in fragment functions at a 32-bit index with its top bit set. Kepler's driver faults on a load outside every buffer, and the draw writes nothing while a later command buffer fails with `kIOAccelCommandBufferCallbackErrorInvalidResource`. Fragment functions run helper lanes for the pixels of a 2x2 quad outside the primitive or scissor rectangle, and ANGLE's buffer-to-texture shaders (`readFromBuffer*TextureFS`, how WebGL uploads from a pixel unpack buffer that needs converting) compute `uint2(position) - textureOffset`, which wraps there: Chrome lost its WebGL context in `texSubImage2D` from PBOs of RGBA4, RGB565, RGB5_A1 and RGB data, and after two GPU process crashes turned WebGL off (Khronos WebGL 2.0.1, deqp `texsubimage2d_pbo`). No buffer on these cards reaches 2^31 bytes, so such an index can only be outside; it reads element 0 instead (`x & ~(x >> 31)`). `NVAIR_FRAGMENT_LOAD_GUARD=0` turns it off. (n07)
- `discard_fragment` as a demote to a helper lane. The plugin's library ends the lane at `discard_fragment` (`llvm.nvvm.discard_fragment` + `llvm.nvvm.exit`), and every derivative its 2x2 quad takes after that came out 0, on all the quad's lanes, even of a value computed before the discard. Metal 2.3 and WGSL make a discarded fragment a helper that runs on for its quad's derivatives, and front ends rely on it: Tint emits `discard_fragment()` and takes `dpdx` after it (WebGPU CTS `statement,discard:derivatives`), and an implicit-LOD sample after an alpha-test discard picked level 0 in the quads along the cut-out's edge. In a fragment function that calls `discard_fragment` itself and takes derivatives, samples a texture or uses quad / SIMD operations, the call sets a private flag instead, the lane runs on, and it is discarded where the function returns; its device stores, atomics and texture writes are skipped once the flag is set. `NVAIR_DEMOTE_DISCARD=0` turns it off. (n10)
- Depth and stencil textures sampled through `texture2d` in ANGLE's shaders: each sample or read of a texture argument comes out (x, 0, 0, 1) when MetalOldCompat item 62's mask (a constant `uint` array at a hidden buffer index) has the texture's bit set. `NVAIR_DEPTH_CHANNELS=0` turns it off. (n11)
- Constant-length copies of 64 bytes or more as loops. The plugin's back end lowers a copy (`llvm.memcpy`, what a struct assignment becomes) to one load and store per word, and its time grew about with the cube of the size: a pipeline copying 168-byte structs between device buffers took 14 s to build, 232-byte ones 37 s, and a WebGPU CTS kernel copying a few such structs (`shader,execution,expression,call,user,ptr_aliasing`) kept the compiler service busy for over 13 minutes, the page waiting for its pipeline. Such a copy (word-aligned, a whole number of words) becomes a loop of word loads and stores, its trip count behind the plugin's opaque `llvm.nvvm.min.u.i32` so the optimizer can't unroll it back: those pipelines build in 1.7 s. `NVAIR_LARGE_COPY_LOOP=0` turns it off. (n12)
- Half vectors spelled as bitcasts in constants. A constant array of `half2x2` (what WGSL `const` f16 matrices become: WebGPU CTS `shader,execution,expression,constructor,non_zero`) reaches the plugin with each `half2` column spelled as a constant expression, `bitcast (<1 x i32> <i32 bits> to <2 x half>)`, and its constant lowering crashed on that (a null dereference): the compiler service died on every try, and Chrome's next pipeline then waited on the compiler forever. A `half2` constant on its own, `half4`, `half3x3` and `float2x2` are spelled plainly and compile. In global initializers each such bitcast becomes the half vector it stands for. `NVAIR_HALF_CONSTANT_FIX=0` turns it off. (n13)
- Cube reads at a level. `read(coordinate, face, [layer,] level)` of a cube or cube array gave level 0's texel at every level above 0, in color and depth formats alike (reads of 2D and 2D-array textures at a level, and cube samples with `level()`, are right; Ivy Bridge's s70 found it by reading every level of a Depth32Float cube array back). The plugin's library reads a cube texel by a `llvm.nvvm.sample.tex.cube[.array].lod` along the direction of its centre with the level as the LOD, but works the direction out from level 0's size (`txq ... lod(texture, 0)`) and samples with a built-in sampler whose LOD clamp is 0 and which has no mip filter. Each such body in the module gets the level's size and the same sampler with a nearest mip filter and the largest LOD clamp (as a `constexpr sampler(filter::nearest, mip_filter::nearest)` is encoded); level 0 reads as before. `NVAIR_CUBE_READ_LEVEL=0` turns it off. (n14)
- Compare-exchange on threadgroup memory. `atomic_compare_exchange_weak_explicit` on a threadgroup atomic that failed left the expected value as it was, instead of the value it found, so the old value came back as the comparand and a compare-exchange loop could spin on a stale value (WebGPU CTS `atomicCompareExchangeWeak` `compare_exchange_weak_workgroup_basic`: every exchange that fails; the device-memory form is right). The plugin's threadgroup body lacks the store into `*expected` that its device body makes where the exchange fails, and marks the pointer read-only; each such body gets the store. `NVAIR_LOCAL_CMPXCHG=0` turns it off. (n18)
- Signed integer vectors to bool. `bool2(int2)` and the other vectors of signed integers gave false for the type's minimum (INT_MIN): the plugin's library tests each lane as `(x & INT_MAX) != 0`, the rule for a float lane, so that -0.0 is false (WebGPU CTS `unary` `bool_conversion:i32`, vec2-vec4; scalars and unsigned vectors are right). The mask is taken out of those bodies, so each lane is `x != 0`. `NVAIR_SIGNED_BOOL_FIX=0` turns it off. (n19)
- Atomics whose operand comes out of a branch. The back end merges an atomic read-modify-write whose operand it takes to be the same in every lane of a warp into one atomic (the value times the number of lanes, or the value once for max, and, ...), and takes a phi to be uniform when its incoming values are. It misses that a phi at the join of a branch on a per-lane condition differs per lane. So `atomic_fetch_add(p, c ? 1u : x)` with `x` uniform (a load from a constant address, a min or max of uniform values), where the front end branches around the load, added one lane's choice for the whole warp, in threadgroup and device memory alike, and another atomic at the same join along with it (mslfuzz.py seed 1744: a threadgroup counter off by multiples of the two values' difference). Each such operand (a phi, or casts, arithmetic and selects over one) goes through a volatile private slot before the atomic, which the back end can't take for uniform. `NVAIR_ATOMIC_JOIN_FIX=0` turns it off. (n25)
- Loads of a private array's element at a constant index. The back end took two loads of the same element at a constant index for one value when the array is also written at a variable index between them: with `v5 = pc[0]` before a loop that loads `pc[0]` again and stores `pc[i]`, `v5` came out as the loop's last `pc[0]`, even with every access to the array volatile (mslfuzz2.py seed 2136 and `VEC=1` seed 1413; the same kernel with the loop's load at `pc[1]`, or either load at an index the back end can't fold, is right). In kernels, each load from a private array that is also accessed at a variable index gets such an index: the constant plus ((the kernel's thread position + k) >> 31), always 0, with a different k for each load, since one shared 0 left the addresses alike to the back end. A kernel without a thread-position argument is left alone, since the back end rejects a special-register read added for it. `NVAIR_PRIVATE_CONSTANT_LOAD_FIX=0` turns it off. Fragment and vertex functions get the same, with the opaque 0 made from the bits of the position's x (a float of at least 0, so below 2^31) or from `vertex_id` (mslfuzz2.py `FRAG=1` seed 2136, the same body as the kernel of seed 2136); `NVAIR_PRIVATE_CONSTANT_GRAPHICS_FIX=0` turns that part off. (n26, n31)
- Overflow checks on 32-bit multiplies. Metal's front end turns `(0xffffffffu / a) < b`, `ulong(a) * ulong(b) > 0xffffffffull` and `(ulong(a) * ulong(b)) >> 32 != 0` into LLVM's `llvm.umul.with.overflow.i32`, and the plugin's own optimizer makes it from the same patterns, but its back end can't select it: the pipeline failed with "Unhandled atom in intrinsic: llvm.umul.with.overflow.i32" (mslfuzz2.py `VEC=1` seed 2478). Every `{u,s}{add,sub,mul}.with.overflow` intrinsic becomes plain arithmetic: the result, and the overflow bit from a compare or from the high half of the exact product. The overflow bits compare against values the optimizer can't see through, since against constants it folded them straight back into the intrinsic between the plugin's optimization passes. `NVAIR_OVERFLOW_FIX=0` turns it off. (n28)
- `madsat` (saturating multiply-add) in big kernels. `madsat(0, 0xfffffffe, c)` came out saturated, `0xffffffff`, instead of `c`, for one thread of 256 in mslfuzz2.py `LONG=1` seed 2245; every small kernel with the same operands, constant or not, was right. The plugin's own body did it, and so did a plain i64 `a * b + c` with the clamp on its high word: that high word came out nonzero for a product of 0, as a carry into it would make it, though the IR the back end received was right. With the carry into the high word computed by a compare instead of a 64-bit add it is right, so each call now gets the adapter's own body without 64-bit adds: 8 and 16 bits in 32-bit arithmetic, 32 bits as the 64-bit product's two words plus `c` with the carry from a compare, then clamped. `NVAIR_MAD_SAT_FIX=0` turns it off. (n30)
- The remainder by a divisor that turns out to be 1. In a big kernel, `0xffffffff % b` with `b = (31 * x) | 1` equal to 1 came out as 766 instead of 0 for one thread (mslfuzz2.py `VEC=1` seed 3841); the same kernel with the operands written out was right. Kepler's division takes its final correction step every time for a divisor of 1, so that step going wrong in some register contexts shows there. Each 32-bit remainder whose divisor isn't a constant now becomes `select(b == 1, 0, original)`: with that the kernel is right, while the same `select` on `b == 2`, an exact equivalent and as much of a change to the code, left it wrong, and so did the very same code with the arm giving the remainder back unchanged, so it is the divisor-1 path and not the code's layout. Remainders only: guarding divisions as well, which no failing kernel needed, made `LONG=1` seed 3034 wrong, while each half alone left it right (the layout-dependent miscompile of the known limitations). The arm goes through an opaque value, since the optimizer drops a `select` whose arms it can prove equal. `NVAIR_DIVISOR_ONE_FIX=0` turns it off. (n32)
- Arithmetic on 3-lane vectors of 8- and 16-bit integers. `ushort3(1, 6, 5) | (ushort3(7166, 18911, 44867) & m)`, with `m.z = ushort(x & 1124510566u)`, lost bit 0 of the constant in lane z (6 for 7) on every thread, while lanes x and y, a `ushort2` or `ushort4` of the same, and the same expression with either mask left out were right (mslfuzz2.py `VEC=1` seed 4480, where it made every thread's result wrong in two words). The IR the back end receives is right; the back end widens a 3-lane vector to 4 lanes in two 32-bit registers, and lane z, beside the undefined fourth lane, is where it goes wrong. Each integer add, sub, mul, shift, and, or, xor, division and remainder on a 3-lane vector of 8- or 16-bit integers is now done lane by lane; Kepler has no packed 16-bit arithmetic, so the lanes were separate instructions anyway. `NVAIR_ODD_VECTOR_FIX=0` turns it off. (n33)
- An unsigned division of a sign-extended 8- or 16-bit value. `(uint)((int)(short)x % 28781) / d`, with `d` not a constant, was wrong whenever the remainder was negative: for `d = 1`, `0xffffbb78` gave `0xffffb901` (mslfuzz2.py `VEC=1` seed 5221, 58 threads' results; the statement alone in a kernel is wrong in 139 of 256 threads). The plugin's optimizer narrows the remainder to 16 bits, so the back end gets `udiv i32 (sext i16 r), d`, and it divides that in floating point as if the dividend had 16 significant bits. That is right for a signed division, but as an unsigned number a sign-extended negative value is close to 2^32, and a float's 24 bits plus one correction step leave the quotient hundreds off. A narrowed signed division, 8 bits and `urem` go the same way; a signed division of the same, the same value sign-extended with shifts (which is what `(int)(short)x` of a 32-bit `x` becomes), a constant `d`, a sign-extended divisor, and 64-bit divisions of a sign-extended `int` are right. The dividend of each 32-bit `udiv` and `urem` that is a `sext` now goes through the opaque minimum, as for the 16-bit products above, which keeps the value and hides the `sext`. `NVAIR_SEXT_DIVIDEND_FIX=0` turns it off. (n34)
- A 2- or 4-lane vector of 8- or 16-bit integers with a constant lane, masked or shifted by constants. `q = (uchar4(201, v1, v2, v3) << uchar4(0, 7, 2, 5)) & uchar4(78, 137, 22, 80)`, then `q.x ^ q.y`, came out `0x40` instead of `0x48` on every thread: lane x, the constant `201 & 78`, lost bit 3 (mslfuzz2.py `VEC=1` seed 7232, where it was a threadgroup index, so every thread's result in a word). The IR the back end gets is right: a vector `shl` by `<0, 7, 2, 5>`, an `and` with a constant, two `extractelement`s and an 8-bit `or` (the optimizer's form of that `xor`, the lanes' bits being disjoint). A `ushort4` goes wrong the same way; a variable lane x, one shift for every lane, a `uchar2`, no mask, `xor` or `or` with the constant, an add of the two lanes, or lane x alone were right. Done lane by lane, the `and` alone fixes the seed, but with shifts of `<0, 7, 0, 0>` the vector shift left over still goes wrong, so each `and` with a constant and each shift by per-lane constant amounts of a 2- or 4-lane vector of 8- or 16-bit integers is now done lane by lane (Kepler has no packed 8- or 16-bit logic or shifts, so the back end took the vector apart anyway). `NVAIR_VECTOR_CONSTANT_FIX=0` turns it off. (n35)
- A saturating add or subtract of a product. `subsat(0xffffffffu, (uint)(uchar)x * 213u)` came out 0 instead of `0xffffffff` whenever the product was 0, and the signed `addsat(a, (int)(uchar)x * 213)` and `subsat`, with the product on either side, came out wrong on every thread (mslfuzz2.py `VEC=1 ASTYPE=1 LONG=1` seed 74, where it was one thread's result). The IR the back end gets is right: a `mul` by the constant feeding `llvm.nvvm.{add,sub}.sat.{s,u}.i32`. The back end folds the multiply into the saturating operation and gets the saturation wrong; for the unsigned subtract it is as if the borrow came from the carry of `a + -b`, which a `b` of 0 never sets. A product with a variable factor, a shift, the plain value, `ushort`, and the unsigned add were right. Each operand of a 32-bit saturating add or subtract that is a `mul` now goes through the opaque minimum, as for the 16-bit products, so the two stay separate operations. `NVAIR_SATURATED_PRODUCT_FIX=0` turns it off. (n36)
- Operations on 2- to 4-lane vectors of 8- or 16-bit integers. In a loop that runs until `all(a != b)` for two `char4` turned false, nested in a loop the optimizer unrolls, the inner loop stopped at the wrong iteration in a few threads (mslfuzz2.py `VEC=1 ASTYPE=1` seed 9923, about 20 threads' results). The condition is right when it is only summed in the same loops, the loops are right without the outer one, and the same lanes compared one by one and combined with `&` are right. Doing only the compare lane by lane left the bug; the `and` of two `char4` that each have constant lanes, feeding the compare, is part of it, and the full kernel needed every such vector operation done lane by lane. With that, `VEC=1` seeds 5171, 5865, 6785 and 7105, until now listed below as layout-dependent, come out right as well: what moved with the code's layout was the back end's handling of these vectors, which it packs into one register. Each integer add, sub, mul, division, remainder, shift, `and`, `or` and `xor` of a 2- to 4-lane vector of 8- or 16-bit integers, each `icmp` of one, and each `zext` or `sext` of a compare's `<N x i1>` to such lanes (which `any` and `all` do) is now done lane by lane; Kepler has no packed 8- or 16-bit arithmetic, so the back end takes these vectors apart anyway. The 3-lane arithmetic and the constant masks and shifts above keep their own switches, which this one follows; selects and conversions done lane by lane as well changed nothing. `NVAIR_NARROW_VECTOR_FIX=0` turns it off. (n37)
- A subtraction of a bitwise not. `tc[((uint)(int)(char)mulhi(c, x) - ~v0) & 63]` read the slot 2 below the right one on 255 of 256 threads, in a kernel that also shifted a 64-bit value by an amount computed from the same `~v0` (mslfuzz2.py `VEC=1 ASTYPE=1 LONG=1` seed 1170; those two statements alone are enough). The IR the back end gets is right: `sub i32 %x, %neg` with `%neg = xor %v0, -1`, the same `%neg` feeding the shift amount. `x - ~v0` is `x + v0 + 1`; the back end, folding the not into the subtraction, computes `x + v0 - 1`. With `x + (v0 + 1)` written out, or a constant shift amount, it is right. Each 32-bit `sub` whose second operand is an `xor` with -1 now becomes `x + (y + 1)`, which is the same value. `NVAIR_SUB_NOT_FIX=0` turns it off. (n38)
- 32-bit products of 16-bit factors (`ushort(a) * ushort(b)`, masks of 0xffff, such values or'ed together): the compiler took the product's top bit for clear, though 0xffff * 0xffff = 0xfffe0001, so `-(int)(~(ushort(a) * ushort(b)) & 0x7fffffff)`, which LLVM makes `(product | 0x80000000) + 1`, came out wrong by 2^31 for large factors (mslfuzz2 `FRAG=1` seeds 111 and 604; kernels too). The same wrong knowledge of a product made `x % (((b | 1) * c) | 1)` off by one in 17% of cases, the `| 1` taken for `+ 1` (mslfuzz seed 645; a divisor that isn't a product is right). One factor of a 16-bit product, and a product an `or` uses, go through an opaque `min` that hides what the optimizer would infer. `NVAIR_NARROW_MULTIPLY_FIX=0` turns it off. (n03)
- `clz` and `ctz` of a constant 0: the plugin's built-in library asks LLVM for counts "undefined for 0", so a constant 0 folded to garbage (`madhi(v, clz(0u), 0u)`), although the GPU gives the width at run time and MSL defines it. Every count asks for the defined result. All 14 kernels of the plain fuzz seeds 1-1000 that the GTX 770 got wrong were this. `NVAIR_COUNT_ZERO_FIX=0` turns it off. (n01)
- MSL 3.1 texture atomics on read_write `texture2d<uint>` / `<int>` had no body (the compiler crashed): each becomes the plugin's own global atomic (`llvm.nvvm.atomic.*`) on the buffer behind the linear texture item 58 makes, at word 64 + y * pitch + x, or on a scratch word of its header when the coordinate is outside the texture or the buffer has no header. Every operation (add, sub, min, max, and, or, xor, exchange, compare-exchange, load as an atomic or with 0, store as an exchange), signed and unsigned, uint and ushort coordinates, in kernels and fragment functions. The function is rebuilt with one hidden buffer parameter per texture its atomics use (`__nvta_<n>`, at the index item 58 binds); the old one stays in the module, empty and renamed, as the plugin keeps pointers to it. `NVAIR_TEXTURE_ATOMICS=0` turns it off. (a01, n04)
- Depth comparisons with gradients (`sample_compare(s, c, ref, gradient2d(...))`, `gradientcube(...)`) had no body for any texture (2D, 2D array, cube, cube array): the plugin's library compares only at a level or with a bias, so the pipeline failed ("Unhandled constant"). Kepler compares only at level 0 (the next fix), so they're made there, through the intrinsic the library's own level form calls: exact for shadow maps of one level. A constant texel offset is kept (the hardware takes it as an immediate). `NVAIR_COMPARE_GRADIENT_FIX=0` turns it off. (n05)
- Not provided: SIMD-group and quad reductions (`simd_sum`, `quad_sum`, prefix sums), `simd_ballot`, `simd_all`/`simd_any`, `simd_is_first` and the active-thread mask. Kepler's back end has no vote instruction or lane mask to build them from (the `ballot` family traps the compiler service: "Compiler encountered an internal error"), and a butterfly of shuffles is only right when all 32 lanes are active. Their compiles still fail, and MetalFX's temporal scaler stays reported unsupported on Kepler (item 44).

`NVAIR_LOG=1` logs what is rewritten and any AIR intrinsic still without a body; `NVAIR_INTRINSICS=0`, `NVAIR_I64_FIX=0` and `NVAIR_SAMPLER_STATE_FIX=0` turn the parts off. The plugin opens its built-in library (`Resources/metal_runtime.metallib`) from its own bundle, so a copy loaded by leaf name (verify.sh) needs the bundle around it. Test use: `DYLD_INSERT_LIBRARIES=build/MetalOldCompat.dylib:Tests/tools/localcc.dylib:build/GeForceAIRCompat-test.dylib`.

## Known limitations
- Ivy Bridge: reading a mipmapped depth 2D array or cube through a texture view that starts at level 1 or higher (a shader `read()` or sample through the view) destroys part of level 0 of another slice: in a 16x16x8 Depth32Float array with 3 levels, a compute pass reading every slice through a level-1 view left 96 texels of slice 4's level 0 at the clear value, for reads and samples alike, and no load/store pass afterwards brings them back (reading the same levels through the whole texture is harmless). It belongs with the HiZ problems of items 63 and 68. The WebGPU CTS reads depth24plus textures back that way to build its expected values, so `textureSampleCompare` `arrayed_2d_coords` and `textureSampleLevel` cube cases fail for depth24plus only.
- Ivy Bridge, Chrome only: in the WebGPU CTS file `web_platform,copyToTexture,ImageBitmap:from_canvas`, copying a flipped (`imageOrientation: "flipY"`) ImageBitmap of a 1x1 or 1x2 canvas reads zeros, but only after the file's unflipped `colorSpaceConversion: "default"` cases have run (211 subcases of the full file; any subset without those passes, and so does every larger size). The bitmap itself is right: reading it once through a 2D canvas before the copy makes every case pass. Chrome's Metal calls for the failing copies match those of passing runs, no shim switch changes it, the installed stack fails the same way, and it doesn't reproduce outside the CTS (same calls in a page of its own, with or without a busy GPU). The R9 and the Iris Pro pass the whole file. Cause not found; real pages are unlikely to hit it.
- Ivy Bridge and Haswell: a gather of the second component (`component::y`) from a cube texture in a 64-bit RG format (RG32Float, RG32Uint) returns the first component's texels (HD 4000 and Iris Pro alike; the R9 is right); 2D and 2D-array textures, RG16 formats and the other components are right. Mesa's i965 driver documents the same Gen7 bug for RG32 gathers of green and works around it per texture format, which a Metal shader doesn't know. WebGPU CTS `textureGather` `sampled_3d_coords` fails for `rg32float` (18 cases).
- Ivy Bridge and Haswell: with mirror-repeat addressing, a coordinate exactly on a texel edge beyond [0, 1] picks the neighbouring texel (nearest filtering, and the footprint of gathers and gather-compares): the hardware mirrors the coordinate and then rounds (u = 1.125 on an 8-texel level becomes 0.875, texel 7), where WebGPU and Vulkan mirror the texel index (texel 9 becomes texel 6). WebGPU CTS `textureSample` `depth_2d_coords` fails its 50 mirror cases on the HD 4000 and the Iris Pro (its spiral sample points land on texel edges; the R9 passes), and so do the mirror cases of `textureSampleLevel` `depth_2d_coords` / `depth_array_2d_coords` and `textureGatherCompare` (fragment). Off the edges, and with repeat and clamp, sampling is right. A shader can't adjust for it without knowing the sampler's address mode.
- Ivy Bridge and Haswell: compute kernels' samplers come from the driver's template (item 40), whose trilinear filter quality isn't full: a gradient sample in a compute kernel blends two mip levels only for LODs between 0.375 and 0.625 ("brilinear"; fragment shaders and samples at an explicit level are full trilinear, and so is the R9). WebGPU CTS `texture_utils:weights` fails in compute. Copying the full-quality bits from the sampler object fixed the gradient samples but made 478 `textureSampleLevel` compute cases (r8unorm and other linear-filtered formats) disagree with the blend weights the CTS measures, so the template's setting is left as it is.
- Ivy Bridge and Haswell: multisampled depth copied in by a texture-to-texture blit holds the right samples (shaders read them all), but a later render pass's depth test doesn't see them (a compare-equal draw at the copied depth fails everywhere; WebGPU CTS `copy_multisampled_depth`, every depth format). Item 27's fix doesn't carry over: rewriting the samples by draws, even one sample at a time through `[[sample_mask]]`, leaves the depth test just as wrong when the depth varies across a pixel, and no compute read or empty pass made the driver catch up. Copying multisampled depth and then testing against it is rare.
- Ivy Bridge's sampler converts some normalized formats to float with less precision than Metal (and WebGPU's read-only storage textures) expect, in shaders' `read()` and `sample()` alike: unorm8 and unorm16 put a few values one ulp low (for unorm8 exactly the powers of two, 1/255 to 128/255, so a shader that reads such a texel back with a truncating `uint(v * 255)` gets one less), snorm16 most of them one ulp off, snorm8 is quantized to steps of 1/255 (1/127 reads 2/255), and RGB10A2's 10-bit channels read v/1024 instead of v/1023. A shader can't put it right without knowing the texture's format. WebGPU CTS `storage_texture,read_only:basic` fails for those formats (304 cases), and `shader_io,fragment_builtins:inputs,*` (position, interStage, front_facing, sample_mask, ...) fails through its truncating read-back of rgba8unorm targets; what's rendered is right. Float and integer formats are exact.
- Ivy Bridge draws points at most 256 pixels wide (Gen7's point width tops out at 255.875): a `[[point_size]]` of 300 or 511, within Metal's documented limit of 511, comes out 256 wide, with `[[point_coord]]` spread over those 256. WebKit's ANGLE reports an `ALIASED_POINT_SIZE_RANGE` of [1, 1] on this GPU, so Safari's WebGL never asks for more.
- Intel (Ivy Bridge and Haswell): a sampler's border colour on integer textures loses its 1s. Through `ClampToBorderColor`, an R32Uint or R16Uint texture with opaque white returns (0, 0, 0, 1) instead of (1, 0, 0, 1), and an RGBA8Uint texture returns (0, 0, 0, 0) for both opaque black and opaque white. Float, unorm and snorm formats match the R9 and an M3, including how missing channels are filled in. Neither WebGPU nor WebGL has border colours, so only native apps that clamp integer textures to the border see it.
- Intel: the integer-texture offset fix (i04) can't see the sampler. A mipmapped integer texture sampled with an offset in a fragment function, through a sampler that doesn't mipmap and minified, reads level 0 with the offset in the selected level's texels: at an LOD of 3, an offset of (-8, 7) lands (-64, 56) texels away. WebKit's ANGLE makes a full mip chain for a one-level GL texture and samples it that way, which fails 12 dEQP `textureoffset` / `textureprojoffset` cases in Safari (`isampler2d_bias`, `usampler2d_bias` and the like); Chrome passes them.
- Ivy Bridge and Haswell: a cube-array comparison at an explicit level on a layer that isn't 0 or a power of two (3, 5, 6, 7, ...) can compare against a reference one ulp off: the fix multiplies the reference by the layer index and iCBE divides it back, which is exact only for powers of two (i79 checks exact ties on layers 0, 1, 2 and 4). It matters only when the reference equals the texel to the last bit.
- Ivy Bridge: a blit from a Depth32Float cube texture's face 2 (+Y) at level 1 into a buffer read level 0's data, while every other face and level, and shader samples and reads of that same face and level, were right (found while writing i78; with or without the shim). Depth cube mips are rarely read back by blit, so it's left as it is.
- Kepler: a private byte or halfword array written and then read at a variable index inside a loop, in a kernel big enough, can read a slot's old value (mslfuzz2 `VEC=1` seeds 1523, 2603, 3890, 4417 and 10949, and `FRAG=1 VEC=1 ASTYPE=1` seed 2126, 2603 and 3890 right with the current code; seeds 1413, 5171 and 5221 were the constant-index loads, the narrow vectors and the sign-extended dividends in section 8, fixed). Giving constant-index stores an opaque index, as section 8 does for loads, made seed 2603 right but broke seed 3890, and rewriting almost any one of 2603's stores alone made it right; seed 4417 came out right as soon as three of its values were written out for inspection, right after they were first set. In 10949 the symptom shows directly: `(uint)pc[i] >> 2` came out with 5, 6 or 7 in its upper halfword, stale upper bits of a byte load, in a kernel that section 8's narrow vectors made go wrong (it is right without them, and wrong in another word without the word form). 2126, a fragment shader with the private-array word wrong on 142 pixels, is likewise right without section 8's narrow vectors or constant masks. Storing a byte computed in 8-bit arithmetic as the same arithmetic done in 32 bits and masked, instead of zero-extended, left 10949 and 2126 as they were. So the miscompile depends on the kernel's layout rather than on one kind of access. It comes from the 32-bit-word form of such arrays (the fix above); every way of avoiding it tried (selects or masks for variable indexes, volatile word accesses) let the array become registers, where the stale upper bits of the byte form came back in more kernels, so the word form stays.
- Kepler: in a big kernel, a few results can come out wrong in a way that depends on the code's layout rather than on any one operation (mslfuzz2 `VEC=1` seeds 7501, 8322, 10023, 11519 and 12616, `VEC=1 ASTYPE=1 LONG=1` seeds 1025, 1837 and 2334, and `FRAG=1 VEC=1 ASTYPE=1` seed 1089; seeds 5865, 6785 and 7105, listed here before, were the narrow vectors in section 8, fixed). Both stay wrong with values written out, but move with unrelated changes: 7501 reduces to two loops in a row, each taking a remainder by a variable divisor, that go wrong with their two statements in one order and not the other; in that reduced form only with section 8's remainder guard, and just as much with the guard giving the remainder back unchanged, comparing an opaque copy of the divisor, or comparing before the remainder, while in the full kernel the guard is what leaves only 2 or 3 threads wrong instead of 25. 8322 goes wrong with section 8's lane-by-lane vector masks and shifts and is right without them; it reduces to a statement with a `short4` masked by a constant and a loop after it, each right on its own with or without that fix, and hiding the constant lane instead of going lane by lane, which leaves 8322 right, leaves seed 7232's miscompile in place, so the lane-by-lane form stays. 11519 is the same: about 40 threads wrong with the lane-by-lane masks, right without; its two masked `uchar4` feed a `select`, and doing the selects lane by lane as well changed nothing. 10023 and 1025 come out right with any one of three unrelated fixes of section 8 turned off, and narrowing them down lands on a statement that only assigns a constant, or on nothing at all once values are written out: where the inspection sits decides whether they go wrong. 1089, a fragment shader, is right with any one of three of section 8's fixes turned off and wrong in more places with two others off. 1837, mostly its private-array word, is right with either the narrow vectors or the remainder guard turned off, and the block it narrows down to is right on its own with every combination of the two. 2334 is right with any one of three fixes off and comes out right as soon as values are written out. 12616 narrows down to a loop that adds `any(uchar3 <= uchar3)` to a value it also compares, with a `uint4` built and indexed before it; it needs both, no fix turned off changes it, the IR the back end gets has no vectors left, and the same compares written lane by lane in the source are right.
- Kepler: one more fuzz kernel (mslfuzz2 `VEC=1` seed 1896) computes `v3 = ((v2 ^ t) % (rhadd(1, v3) | 1)) / C` wrong in a `switch` case for 3 of 256 threads, with every adapter switch off too. Reduced to 54 lines, it still needs two private arrays and threadgroup traffic it doesn't read (without them it's right), and the same statement alone is right over 262 144 random inputs, inside a `switch` too: a register-context miscompile in the back end that can't be located without Kepler disassembly.

- Kepler (GTX 770) converts a fragment color of exactly 0.5 to 127 in an 8-bit unorm target, where Apple's GPUs give 128: 127.5 is a tie, and the MSL specification (8.7.1.2) asks for round-to-nearest-even (128). It's within the 0.6 ULP D3D allows, and Kepler's color output does the conversion in fixed function after the shader, so the compiler can't round for it (it doesn't know the target's format or blending). s61 checks that tie on its own and expects 127 on Kepler (its argument-buffer checks use values that aren't ties).
- Kepler's texture atomics (item 58) need a texture created with `MTLTextureUsageShaderAtomic`, 2D, one level, R32Uint or R32Sint: on a 2D array, 3D or 1D texture (no linear form on Kepler), a texture from a heap, or one made without that usage they do nothing. Kepler has no SIMD-group or quad reductions, ballot or vote (no lane mask to build them from): those compiles still fail. A depth comparison with gradients and a computed (not constant) texel offset still has no body.
- On Kepler a depth comparison can't use a level above 0: a mipmapped shadow map sampled at a higher level, with a bias or with gradients compares against level 0.
- On Kepler `write(color, coordinate, [slice,] level)` with a level above 0 writes level 0 (2D, 2D array, cube, cube array and 3D alike; Haswell and the R9 M370X write the level). The plugin stores through a surface, which binds one level, and drops the level argument. Writing each level through a one-level texture view (`newTextureViewWithPixelFormat:textureType:levels:slices:`) works, and is what Dawn (WebGPU), ANGLE and MoltenVK do.
- Kepler clamps depth to [0, 1], not to the viewport's depth range, when depth clipping is off (`MTLDepthClipModeClamp`, WebGPU `unclippedDepth`): with a viewport depth range of [0.25, 0.75], a fragment beyond it gets depth 0 or 1 instead of 0.25 or 0.75 (WebGPU CTS `depth_clip_clamp`, every `unclippedDepth=true` case). The full [0, 1] range, the usual case for shadow maps, is right.
- Kepler's constant depth bias on Depth32Float is twice WebGPU's for a primitive whose depth is exactly a power of two (the scale is implementation-defined in OpenGL): z = 0.25 with a bias of 2^23 gives 0.75, where WebGPU expects 0.5 (WebGPU CTS `depth_bias`, 1 of 16 cases).
- Item 62 gives depth and stencil textures (d, 0, 0, 1) only in ANGLE's shaders (WebGL in Chrome, Firefox and Safari). Other Metal code that samples a depth texture through `texture2d<float>` still gets (d, d, d, d) on Kepler; Metal leaves those channels undefined, and `depth2d` is what depth sampling is meant to use.

- Metal's validation layers don't run on this stack (item 41 switches them off): API and shader validation need the OS's own Metal runtime and compiler.
- A shader that crashes the compiler service costs the app time: MetalOld waits for the service to come back and tries the compile once more (about 20 s), and the app's next compile waits for launchd to restart the service (about 10 s). After many crashes in a row it can be worse: in Chrome on Kepler, a WebGPU test whose pipelines crashed the compiler a dozen times left the next pipeline creation waiting for the service's reply for over 10 minutes (MetalOld's `XPCCompilerConnection::checkConnectionActive`), with the service idle. Each fix here that keeps a shader from crashing the compiler removes one of these stalls; wgpu's render ICB probe was one on the Iris Pro (gfx-rs/wgpu#10927).
- On Tahoe, a shader that reads a multisampled 2D array texture (`texture2d_ms_array`) doesn't compile on the R9 M370X: OCLP's `libLLVM_helper` aborts while converting it for the 14.2 compiler, with the stock files too. On Sequoia they compile, `depth2d_ms_array` reads work on both, and the Iris Pro has no multisampled array textures at all.
- The R9 M370X's compiler can't build a depth comparison with gradients (`sample_compare(..., gradient2d(...))`, n05; fragment functions too). - A struct that points to itself (`struct L { device L *next; int v; }`) still leaves an entry in the map patch 5 fixes, because the objects keep each other alive and are never destroyed. The memory stays valid, so it can't crash the way patch 5's case did. 300 kernels with different layouts, each writing through its struct on the GPU, gave no crash and no wrong write, with 63 entries left at the end. A later compile whose metadata lands on such an address could in principle read the old layout. I haven't seen that.
- On Ivy Bridge, a gather of the fourth component (`component::w`) from an integer texture without alpha (R and RG formats) returns the bits of 1.0f (1065353216) instead of 1 (a17 on the HD 4000). Sampling and reading such textures return 1. Haswell selects the channel in the surface state, which Ivy Bridge lacks, and a shader can't tell those formats from RGBA32 ones whose alpha holds the same bits. Only the WebGPU CTS gathers that component.
- On Ivy Bridge, textures and samplers inside argument buffers aren't emulated (c01 fails with "Compilation failed"). Item 47 covers buffer pointers, arrays of them and constants, which is what WebKit's ANGLE puts there for WebGL 2 uniform blocks. Safari's WebGPU would need the rest, and Apple keeps it off on Sequoia.
- On the Ivy Bridge driver, stencil at mip level 2 or higher holds nothing through blits (a copy in and straight back out returns 0 at any size; levels 0 and 1 and every slice are right), and shaders reading stencil at level 1 or higher through a view get 0 (Gen7 can't sample its separate stencil format, W-tiled, directly; Mesa keeps an R8 copy of it for that). So s37, s41, s43 and s48 (level 2) and s46 (a view of level 1) still fail. Render passes there go through item 33's temporaries and the blits. WebGL renders stencil at level 0, and no app I know of mipmaps stencil; this is WebGPU CTS ground.
- On Ivy Bridge, a single-sample Stencil8 texture attached as stencil only still loses the stencil of draws whose fragment function writes `[[sample_mask]]`: a Stencil8 texture can't be attached as depth, which is what s67's fix does for combined formats. ANGLE writes the sample mask only when it renders multisampled, and multisampled Stencil8 is made Depth32Float_Stencil8 (s40), so WebGL doesn't hit it.
- Stencil8 textures read wrong beyond slice 0 of level 0 (blits are right), in Safari and Firefox; Chrome avoids it by using a combined format. The T# layout looks wrong; a fix would mean remapping Stencil8 to a combined format in the driver.

Runtime subnormals are flushed to zero, which is allowed. Only constant tables with subnormal values reach it, so it isn't worked around.
